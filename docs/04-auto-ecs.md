# 4. 자동 ECS 변환

프로그래머는 객체지향 클래스를 쓰고, 컴파일러가 데이터 지향 ECS로 분해합니다. Unity DOTS에서 사람이 하던 `IComponentData`/`SystemBase` 분해를 컴파일러가 합니다.

## 4.1 파이프라인

```
엔티티 클래스 ──▶ ① 필드 접근 분석 ──▶ ② 컴포넌트 클러스터링 ──▶ ③ 아키타입 구성
                         │                                            │
                         ▼                                            ▼
                 ④ 시스템 추출 (Update, client 메서드, Game.Update)
                         │
                         ▼
        ⑤ 읽기/쓰기/지연쓰기 집합 ──▶ ⑥ 해저드 탐지 ──▶ ⑦ 스테이지 스케줄링 ──▶ ⑧ 병렬화 판정
```

## 4.2 ① 필드 접근 분석

모든 함수를 호출 그래프를 따라 분석해서 필드마다 다음을 수집합니다.

- **자기 접근**(self): `this.F` 또는 암묵적 `F` — 행(row) 인덱스로 직접 접근
- **원격 읽기**(remote read): `other.F` — 스냅샷 읽기
- **원격 쓰기**(remote write): `other.F op= v` — 지연 명령. `+=, -=`는 **교환 가능**으로 표시. 범위가 있는 필드는 명령 하나를 적용할 때마다 포화하므로 순서가 결과를 정하고(80에 +60, −50은 50, −50, +60은 90), 그 순서는 보내는 엔티티의 행 순서로 고정이라 결과는 결정론적입니다
- 어느 시스템에서 접근하는지
- **임의 행 접근인지**: 엔티티 핸들을 통한 읽기(`this`·쿼리 커서가 아닌 것), 지연 명령·메시지의 대상, 다른 엔티티가 부르는 메서드 안의 자기 접근은 "임의의 행"을 건드립니다. 나머지는 자기 행을 순서대로 훑는 **스트리밍** 접근입니다.

자기 메서드 호출(`Fire()`)은 인라인처럼 따라가며, 상속 시 아키타입별로 **정적 디스패치** 대상을 결정한 뒤 따라갑니다.

## 4.3 ② 컴포넌트 클러스터링 — 접근 서명(access signature)

데이터베이스의 수직 분할(vertical partitioning)과 같은 원리입니다.

> 필드 f의 **접근 서명** = f를 접근하는 시스템들의 집합 (+ 복제 여부)
> **같은 서명을 가진 필드는 하나의 컴포넌트로 묶는다.**

이유: 같은 시스템들이 항상 함께 읽는 필드는 같은 캐시 라인에 있어야 하고(AoS 내부), 서로 다른 시스템이 읽는 필드는 분리되어야 불필요한 메모리 대역폭을 쓰지 않습니다(SoA 외부). 이는 고전적 구조체 분할(structure splitting / peeling)과 hot/cold 분리를 시스템 단위로 자동화한 것입니다.

```
examples/arena.sijo 의 실제 결과 (sijoc explain):

Ship 필드                  접근 서명                                        → 컴포넌트
Pos                        Ship.Update, Ship.Render, Bullet.Update, 복제됨  → Ship_C0 { Pos }
Vel, Cooldown, Target      Ship.Update                                      → Ship_C1 { Vel, Cooldown, Target }
Hp, Kills                  Ship.Update, Bullet.Update(원격)                 → Ship_C2 { Hp, Kills }
Side                       Ship.Update, Ship.Render, 복제됨                 → Ship_C3 { Side }
Shots (쓰기만 하고 읽지 않음)                                               → 제거 (dead field elimination)
```

`Bullet.Update`는 총알마다 모든 배의 `Pos`를 훑지만 `Vel`/`Cooldown`은 건드리지 않습니다. 분리 덕분에 그 루프는 `Pos`만 담긴 연속 배열(8바이트/배)을 읽습니다.

- 시스템에서 전혀 접근하지 않고 초기화에만 쓰이는 필드 → **cold** 컴포넌트.
- **스트리밍 필드는 필드마다 열 하나**로 나눕니다(완전 SoA). 같은 서명이라도 자기 행 루프로만 접근되는 필드는 묶어 둘 이유가 없고, 열로 나뉘어야 행 루프가 SIMD로 벡터화되며 조건부 저장도 열 단위로 됩니다. 임의 행으로 읽히는 필드는 묶어 두어 한 번의 캐시 미스로 함께 읽게 합니다(위 표의 `Pos`·`Hp, Kills`). 행 루프 안에서는 그 행의 필드를 지역 변수에 읽어 두었다가 끝에 한 번 씁니다(측정: `bench/RESULTS.md`의 particles).
- 어디서도 읽지 않는 필드 → 저장소에서 **제거**, 쓰기는 부수효과만 남김. 판단은 소스에 적힌 대로의 읽기로 합니다(최적화가 `e.Tries * 0`처럼 읽기를 없애도 저장소는 남음). 그래서 저장되는 월드·체크섬·상태 파일은 최적화의 강도와 무관합니다.
- `[Component("Name")]`으로 수동 지정 가능.

## 4.4 ③ 아키타입

엔티티 클래스 하나 = 아키타입 하나입니다. 상속 `class Fighter : Ship`의 아키타입은 Ship의 컴포넌트 + Fighter 고유 컴포넌트입니다. Ship의 컴포넌트 타입은 공유되므로 `Query<Ship>()`은 Ship과 Fighter 테이블을 모두 순회합니다. 프로그램이 런타임에 붙였다 떼는 컴포넌트(`component`, 1.16절)를 쓰면 아키타입은 (클래스, 붙은 컴포넌트 집합)이고, 조합마다 같은 방식의 테이블이 하나씩 있습니다(4.4.1절).

제네릭 엔티티 클래스(1.14절)는 쓰인 타입 인자마다 엔티티 클래스가 하나씩 생기므로 `Pool<int>`와 `Pool<SVec2>`는 아키타입이 따로입니다. 컴포넌트 클러스터링·죽은 필드 제거·시스템 추출·해저드 탐지도 인스턴스마다 따로 하므로, `Pool<SVec2>`에서만 읽히지 않는 필드는 `Pool<SVec2>` 테이블에서만 빠집니다. `class IntPool : Pool<int>`의 아키타입은 `Pool<int>`의 컴포넌트 + IntPool 고유 컴포넌트이고 `Query<Pool<int>>()`는 둘을 돕니다.

### 4.4.1 동적 아키타입과 컴포넌트 조합

런타임에 붙였다 떼는 상태(`Burning`, `Stunned`)와 Verse Scene Graph식으로 컴포넌트를 조합한 엔티티를 위한 기능입니다. 문법은 1.16절에 있습니다. 여기서는 컴파일러가 이것을 어떻게 지금의 ECS(고정된 아키타입, SoA 테이블, 시스템 규칙)로 바꾸는지 설명합니다.

```csharp
public component Burning                 // 데이터 + 메서드, 엔티티에 붙음
{
    public mut int Left = 3;
    public int in 0..9 Power = 1;
    public void Update(float dt)         // Burning이 붙은 엔티티마다 도는 시스템
    {
        Left -= 1;
        if (Owner is Ship s) { s.Hp -= Power; }   // Owner = 이 컴포넌트를 가진 엔티티
        if (Left <= 0) { Remove<Burning>(); }
    }
}
ship.Add(new Burning { Left = 5 });      // Spawn처럼 지연 구조 변경
ship.Remove<Burning>();
if (ship.Get<Burning>() is Burning b) { b.Left += 2; }   // 읽기는 시스템 시작 시점, 쓰기는 지연
foreach (var (s, b) in Query<Ship, Burning>()) { ... }  // 같은 엔티티를 Ship과 Burning으로
```

**의미: 구조 변경도 시스템 규칙을 따릅니다.** `Add`/`Remove`는 `Spawn`/`Destroy`처럼 시스템 끝에 명령 순서대로 적용되는 구조 변경입니다. 시스템 끝의 적용 순서(4.9절)에서는 원격 쓰기·메시지 → 파괴 → **컴포넌트 붙이기·떼기(명령 순서)** → 생성 순입니다. 그래서
- 같은 컴포넌트를 두 번 붙이면 나중 값으로 바뀌고, 없는 것을 떼면 아무 일도 없습니다. 한 시스템에서 `Remove` 뒤 `Add`이면 다시 붙은 상태, `Add` 뒤 `Remove`이면 없는 상태로 끝납니다.
- 파괴되는 엔티티에 붙이는 것은 버려지고, 이 시스템에서 생성된 엔티티(아직 없음, 4.9절)에 대한 `Add`/`Remove`도 쓰기와 마찬가지로 버려집니다.
- `Has`/`Get`과 쿼리는 시스템 시작 시점의 조합을 봅니다. `Add` 바로 뒤의 `Has`는 아직 `false`입니다. 메시지도 같은 플러시의 구조 변경보다 먼저 실행되므로 시작 시점의 조합을 봅니다.
- 다른 엔티티의 컴포넌트는 핸들로 닿으므로 원격 접근입니다: 읽기는 스냅샷, 쓰기(`b.Left += 2`)와 메서드 호출(`b.Fuel(5)`)은 지연 명령입니다. `Owner`도 핸들이므로 `Owner is Ship s` 뒤의 `s.Hp -= 1`은 지연 `+=`입니다(같은 엔티티라도 핸들 접근은 다른 엔티티로 취급, 4.9절 3).
그래서 결과는 지금처럼 스레드 수와 무관합니다(테스트: 1/4 스레드, 샤드 3개, 새니타이저).

**아키타입 = (클래스, 붙은 컴포넌트 집합).** 프로그램의 모든 `Add`/`Remove`는 어느 엔티티에 닿을 수 있는지 정적으로 압니다: 받는 쪽의 정적 타입(`Ship`이면 Ship과 하위 클래스, 인터페이스면 구현한 클래스, 컴포넌트 타입이면 그 컴포넌트를 가진 엔티티), 받는 쪽이 없으면 그 메서드의 클래스(컴포넌트의 메서드면 그 컴포넌트를 가진 엔티티). `components` 패스(효과 분석 직전)는 이것으로 클래스마다 **빈 집합에서 출발해 도달할 수 있는 컴포넌트 집합**을 너비 우선으로 셉니다. 컴포넌트 A의 메서드 안의 `Add(new B { })`는 A가 있는 집합에만 적용되므로, 예를 들어 `B`는 `A`를 거쳐서만 생기는 프로그램의 Ship 테이블은 `Ship`, `Ship+A`, `Ship+B`, `Ship+A+B` 넷입니다. 빈 집합이 아닌 조합마다 **조합 아키타입**(`Ship+Burning`, 그 클래스의 하위 클래스로서 컴포넌트의 필드를 더 가짐)을 만들면, 그 뒤의 모든 단계(효과, 클러스터링, 스케줄, 테이블, 해저드, 공간 격자, 복제, 저장, 체크섬)는 지금의 아키타입을 그대로 다룹니다. `Query<Ship>()`은 Ship의 모든 조합 테이블을 돌고(상속과 같은 방식), `Query<Ship, Burning>()`은 Burning이 있는 Ship 조합만, `Query<Burning>()`은 Burning이 있는 모든 클래스의 조합을 돕니다. `Has<Burning>()`은 슬롯의 아키타입 번호에 대한 마스크 검사이고, 자기 자신에 대해서는 아키타입마다 컴파일 타임에 정해집니다.
- 한 클래스의 조합 테이블은 **16개까지**입니다(자기 자신 포함, 서로 독립인 컴포넌트 4개 = 16조합). 아키타입 소속은 64비트 마스크로 검사하므로 프로그램 전체의 아키타입도 64개까지입니다(E0266). 조합 순서는 컴포넌트 수가 적은 것부터, 같으면 선언 순서이고, 시스템이 도는 테이블 순서는 클래스 바로 뒤에 그 조합들입니다.
- **열린 테이블(16조합 초과)**: 도달할 수 있는 조합이 16개보다 많은 클래스는 조합마다 테이블을 두지 않고 **테이블 하나**에 그 클래스가 가질 수 있는 모든 컴포넌트의 열과 숨은 필드 `__comps`(컴포넌트마다 한 비트, 32종류까지; 넘으면 E0266)를 둡니다. `Add`/`Remove`는 행을 옮기지 않고 같은 명령 적용 순서로 비트를 켜고 끕니다(`Add`는 컴포넌트의 모든 필드를 실은 값으로 채우고, `Remove`는 비트를 끄고 컴포넌트의 리스트를 해제). `Has<C>()`·`Get<C>()`는 아키타입과 그 행의 비트를, `Query<T, C>()`·`Query<C>()`·`Count<C>()`·컴포넌트 시스템은 비트가 없는 행을 건너뜁니다. 비트는 일반 필드라서 결정론·스레드·샤드·체크섬·상태 파일이 그대로 적용되고, 클라이언트도 `Has`를 검사하도록 항상 복제됩니다(컴포넌트 수만큼의 비트로 양자화). 조합 테이블로 저장된 상태(`arch Ship+Burning`)는 열린 테이블로 들어오며 저장된 컴포넌트가 비트가 됩니다(조합 테이블 시절의 상태에서 이어 가는 라이브 코딩). 한 테이블이라 메서드는 한 번만 컴파일되고 붙이고 떼기는 싸지만, 컴포넌트의 열은 그 컴포넌트가 없는 행에도 자리를 차지하고 컴포넌트 시스템은 클래스의 모든 행을 훑습니다. 테이블의 행은 생성 순서(파괴만 swap-remove)이므로 열린 테이블의 엔티티는 조합별이 아니라 행 순서로 방문됩니다: 결과는 스레드·샤드와 무관하게 결정적이지만, 방문 순서에 따라 이기는 쓰기(같은 시스템에서 여러 엔티티가 같은 대상에 `Add`하는 경우 등)는 조합 테이블과 다를 수 있습니다. `sijoc build --open-tables`는 컴포넌트를 얻는 모든 클래스를 열린 테이블로 만듭니다(테스트가 두 배치를 비교: 손으로 확인한 `components.sijo`의 틱별 출력이 같고, `opentable.sijo`는 64조합을 따로 만든 모델과 틱마다 같음). `sijoc explain`이 `class Hero: one open table ...`로 알려 줍니다. 새 조합이 생겨도 테이블을 새로 만들지 않으므로, 시스템 스케줄·해저드·복제·샤드 코덱·상태 파일은 컴파일 타임에 정한 아키타입 목록 그대로입니다.
- **코드 크기와 공유**: 한 클래스의 메서드는 그 클래스의 모든 조합 테이블에서 **한 번만** 컴파일되고, 컴포넌트의 메서드도 그 컴포넌트가 있는 모든 테이블(다른 클래스 포함)에서 한 번만 컴파일됩니다. 공유된 코드는 테이블 이름 대신 **뷰**(`SijoView_N`: 테이블의 열 포인터와 아키타입 번호, 시스템 루프마다·호출마다 한 번 만듦)로 자기 행에 닿고, 자기 자신의 `Has<C>()`는 뷰의 아키타입 번호로 검사합니다(그 클래스의 조합들 사이에서 효과·재정의·행 캐시가 모두 같을 때 공유; `--gpu`로 장치에 가는 메서드는 테이블별 그대로). 그래서 `components.sijo`(아키타입 20개)의 메서드 인스턴스는 12개입니다(`sijoc explain`: `compiled once (through a view of each table's columns): the methods of Ship on its 8 tables; ...`). 남은 크기는 테이블마다의 연산(테이블 조작, 복제·샤드 코덱, 상태 파일)과 메서드 밖에서 클래스를 도는 쿼리 루프의 테이블별 펼침이고, 조합 수에 비례합니다(곱은 아님).
- **행 이동**: 붙이고 떼기는 행을 같은 클래스의 다른 테이블로 옮기는 일입니다(`sijo_move_A_B`: 새 테이블 끝에 붙이고 두 테이블에 공통인 열을 복사, 옛 테이블은 swap-remove). 엔티티 핸들은 (슬롯, 세대)이고 슬롯이 아키타입과 행을 가리키므로 슬롯만 고치면 모든 핸들이 그대로 유효합니다. 클래스 필드의 리스트·문자열·코루틴 프레임은 행과 함께 옮겨지고(소유권 이동, 해제 없음), 컴포넌트 열은 그 컴포넌트가 있는 테이블에만 있습니다. 붙이는 값은 `Add`가 계산해 명령 버퍼에 담습니다(필드 기본값 위에 초기화 목록, 범위 필드는 적용할 때 포화).

**시스템·스케줄.** 컴포넌트의 `Update`(와 `client` 메서드)는 그 컴포넌트가 있는 모든 테이블을 도는 시스템이고, 선언 순서에서 컴포넌트의 자리에 놓입니다. 컴포넌트 메서드는 가상이 아니므로 그 클래스에 같은 이름의 메서드가 있어도 섞이지 않습니다. `this`는 컴포넌트(필드는 자기 접근: 행 루프의 직접 접근), `Owner`는 엔티티 핸들입니다. 효과 분석은 `Add`/`Remove`를 "자기 조합을 바꿈"과 "클래스 C의 조합을 바꿈"으로 기록하고, 스케줄러는 그 클래스의 **모든 조합 테이블**의 존재와 모든 컴포넌트를 구조 변경(4.7절의 S)으로 봅니다. 그래서 컴포넌트를 바꾸는 시스템과 그 클래스를 읽는 시스템은 같은 스테이지에 놓이지 않습니다. 구조 변경은 스레드별 명령 버퍼에 쌓았다가 행 순서로 합치므로 병렬 실행을 막지 않습니다. 컴포넌트 필드는 자기 접근 서명으로 클러스터링됩니다(4.3절, `Burning_C0 { Left }`). `sijoc explain`이 조합 테이블, 컴포넌트마다 그것을 가질 수 있는 클래스, 시스템마다 `adds/removes components of self` 같은 효과를 보여 줍니다.

**복제·저장.** 엔티티의 아키타입 번호가 곧 컴포넌트 비트 집합이고, 스냅샷은 엔티티마다 이미 아키타입 번호를 보냅니다(5.5.3). 조합이 바뀐 엔티티는 같은 슬롯·세대의 새 아키타입으로 보내지고 클라이언트는 그 엔티티를 새 테이블에 다시 만듭니다(그 엔티티의 복제 값 전체를 한 번 보냄, 5.9절). 컴포넌트 필드는 일반 필드처럼 범위·양자화·더티 플래그·델타를 거치고, 클라이언트 코드는 `Has`/`Get`과 컴포넌트 필드를 읽습니다. 상태 파일은 테이블을 `arch Ship+Burning`, 컴포넌트 필드를 `field Burning.Left int`처럼 이름으로 적습니다. 새 프로그램에 그 조합이 없으면(컴포넌트를 지웠거나 더는 도달할 수 없으면) 같은 클래스에서 저장된 컴포넌트를 가장 많이 가진 테이블로 옮기고 `components-dropped:Ship+Burning+Wet`으로 알립니다. 그래서 라이브 코딩의 이름 기반 이주(10.3절)가 그대로 됩니다.

**생성과 함께 붙이기**: `Spawn(new T { }, new C { })`가 주는 컴포넌트 집합도 그 클래스의 출발점이 되어 조합을 셀 때 들어가고, 그 `Spawn`은 조합 테이블에 바로 행을 만듭니다(효과·병렬 생성 테이블·샤드 생성 레코드는 그 조합 아키타입 그대로).

**문자열·컬렉션 필드와 코루틴**: `Add` 명령은 평범한 값을 struct로, 문자열·리스트·배열을 그 뒤에 메시지 인자와 같은 바이트로 싣습니다(`SIJO_CMD_CADD`, 스레드·샤드·네트워크를 그대로 건넘). 적용할 때 새 행의 기본값(또는 다시 붙일 때의 옛 값)을 해제하고 풀어 넣으며, `sijo_move_A_B`는 떨어지는 컴포넌트의 리스트를 해제합니다. 컴포넌트의 `async` 메서드는 프레임 필드가 컴포넌트의 필드라서 그 컴포넌트가 있는 조합 테이블에만 있고, 떼면 사라집니다.

**남은 것**: 컴포넌트를 담는 필드·매개변수·컬렉션(E0263: 엔티티 핸들을 담고 필요할 때 `Get`), 컴포넌트 필드의 사전·델리게이트(E0264).

**근접 질의**: `foreach (var (o, g) in Query<Mote, Glowing>())`도 거리 조건이 증명되면 공간 격자로 갑니다(4.12절). 격자는 질의가 도는 조합 테이블(그 컴포넌트가 있는 것)마다 하나씩 만들어지고, 루프는 그 테이블들을 차례로 돌며 별칭 커서(`g`)도 같은 행을 가리키므로 결과는 전체 순회와 비트 단위로 같습니다. 샤드의 헤일로도 그 테이블들에 대해 계산합니다.

## 4.5 ④ 시스템 추출

| 소스 | 시스템 |
|---|---|
| 엔티티 클래스의 `Update(float dt)` | 그 메서드를 *최종 구현으로 갖는* 아키타입들을 순회하는 시스템 |
| `client` 메서드 | 클라이언트 월드에서 도는 클라이언트 시스템 |
| `Game.Update(float dt)` | 전역 시스템 (마지막, 단일 실행) |

`override`로 재정의하면 아키타입별로 다른 시스템이 됩니다 — 가상 호출이 사라집니다.

## 4.6 ⑥ 해저드 탐지와 자동 이중 버퍼

시스템 규칙(0장)에 따르면 다른 엔티티는 "시스템 시작 시점" 값으로 읽힙니다. 그런데 **같은 시스템이 어떤 컴포넌트를 자기 쓰기도 하고 원격 읽기도** 하면(예: Boids — 이웃의 `Pos`를 읽고 자기 `Pos`를 씀), 순진한 구현에선 순회 순서에 따라 결과가 달라집니다(Gauss-Seidel).

컴파일러는 이를 **해저드**로 탐지하고 그 컴포넌트만 이중 버퍼링합니다.

```c
sijo_par_copy(t->c0_prev, t->c0, n * sizeof(Boid_C0));   // 시스템 시작 시 1회 (스레드가 나눠 복사)
t->c0_read = t->c0_prev;                          // 원격 읽기는 이전 값 버퍼로
for (row...) Boid_Update(row);                    // 자기 쓰기는 c0에 직접
t->c0_read = t->c0;
```

결과: 순회 순서와 무관한 Jacobi 의미론 → **결정론 + 완전 병렬**. 비용은 해당 컴포넌트를 한 번 복사하는 것뿐이며, 그것도 **다른 엔티티가 실제로 읽는 필드만** 복사합니다(컴포넌트의 나머지 필드는 복사하지 않음). 큰 테이블은 스레드들이 나눠 복사합니다. `mut`이 없는 필드는 생성 뒤에 쓰이지 않으므로 해저드가 되지 않습니다(1.6.2절).

## 4.7 ⑦ 스테이지 스케줄링

두 시스템 A(먼저), B가 **충돌**한다는 것은:

```
(W_A ∪ D_A ∪ S_A) ∩ (R_B ∪ W_B ∪ D_B ∪ S_B) ≠ ∅   또는 그 역
W = 자기 쓰기 컴포넌트, D = 지연 쓰기 컴포넌트, R = 읽기, S = 구조 변경(Spawn/Destroy한 아키타입의 모든 컴포넌트)
```

스케줄러는 소스 순서를 따라 각 시스템을 "충돌하는 앞선 시스템의 마지막 스테이지 + 1"에 배치합니다 (리스트 스케줄링). 같은 스테이지의 시스템들은 동시에 실행될 수 있고, 결과는 순차 실행과 **동일함이 보장**됩니다. Bevy는 충돌하는 시스템의 순서가 지정되지 않으면 "모호성(ambiguity)" 경고를 내지만, Sijo는 소스 순서라는 결정론적 기본값이 있어 모호성이 존재하지 않습니다.

## 4.8 ⑧ 병렬화 판정

시스템 규칙 덕분에 엔티티 순회는 원칙적으로 항상 병렬화할 수 있습니다. 엔티티 시스템은 OpenMP로 엔티티 단위 병렬 실행하고(행이 `SIJO_PAR_MIN` = 256개 이상일 때), 다음 경우에만 직렬로 돕니다. 이유는 `sijoc explain`에 나옵니다.

- `Print`가 있음 (출력 순서)
- `atomic` 안에서 직접 `Spawn`함(블록이 부른 메서드가 생성하는 것은 병렬로 돌고, `fail`하면 그 스레드의 생성 테이블에서 버려짐), 또는 `Spawn`이 돌려준 핸들을 아래에서 고칠 수 없는 방식으로 씀. `Spawn`은 스레드별 생성 테이블에 쌓았다가 행 순서로 합치므로 병렬로 돌아도 직렬 실행과 같은 ID를 받습니다. 돌려준 핸들은 그때까지 **임시 핸들**(스레드·행 번호)이며, 합친 뒤 진짜 핸들로 고칩니다. 그래서 임시 핸들은 `this`의 핸들 필드나 지역 변수에 담기, `==`/`!=` 비교, `is` 검사(이 시스템에서 생긴 엔티티는 직렬 실행처럼 아직 없음), 메시지·원격 쓰기·`Destroy`의 대상으로만 쓰면 됩니다. 그 밖의 사용(리스트에 넣기, 다른 엔티티의 필드에 쓰기 등)이 있으면 직렬로 돕니다.
- `[Pure]`도 `[Deferred]`도 없는 `extern` 함수 호출 (외부 효과; `explain`이 그 함수 이름을 직렬 이유로 보여 주고 린트 L409가 호출 지점을 가리킴). `[Deferred]` extern의 호출은 인자와 함께 스레드별 명령 버퍼에 쌓였다가 스테이지 끝에 명령 순서대로 실행되므로 병렬을 막지 않습니다(1.11절)
- `Game.Update`(전역 시스템)와 클라이언트 시스템

원격 쓰기·파괴·원격 호출은 **스레드별 명령 버퍼**에 쌓은 뒤 행 순서로 병합하므로 병렬 실행을 막지 않습니다. 스레드 수는 `OMP_NUM_THREADS`나 임베딩 API의 `set_threads`(1~64)로 정하며, 결과는 스레드 수와 무관하게 비트 단위로 같습니다.

**시스템 간 태스크 병렬.** 같은 스테이지의 시스템들은 서로 쓰는 것을 건드리지 않으므로(4.7절) 동시에 돌아도 됩니다. 스테이지 안에서 연달아 오는 시스템 중 Spawn이 없고, 근접 격자를 만들지 않고, 직렬 사유가 `Print`뿐인 엔티티 시스템들은 **태스크 그룹**이 됩니다(`sijoc explain`의 `task group`). 그룹은 매 틱 구성원마다 행 수를 보고, 모두 자기 병렬 임계값보다 작으면(각자는 엔티티 단위로 병렬화할 만큼 크지 않으면) 구성원마다 스레드 하나씩 나란히 실행합니다. 구성원 j는 스레드별 칸 j+1(명령 버퍼·프레임 아레나·엔티티 문맥)을 쓰고, 끝나면 칸 순서 = 스테이지 순서로 명령을 합치므로 지연 명령이 적용되는 순서가 직렬 실행과 같습니다. 구성원 중 하나라도 크면 평소처럼 하나씩(각자 엔티티 단위 병렬로) 돕니다. 스레드 1개에서는 언제나 하나씩 돕니다.

**프로파일 기반 결정(PGO).** 프로그램을 `--profile FILE`로 실행하면 스레드 하나로 시스템마다 걸린 시간과 행 수, 스테이지마다 지연 명령 적용 시간, 그 기계에서 병렬 영역 하나를 여닫는 비용을 FILE에 씁니다. `sijoc build --profile-use FILE`은 이것으로
- 시스템마다 병렬 임계값을 정하고(행 하나의 비용 × 행 수가 병렬 영역 비용의 두 배를 넘는 행 수; 기본은 모든 시스템 256행),
- 태스크 그룹을 측정한 작업량으로 판단하고(합이 병렬 영역 비용의 두 배에 못 미치는 그룹은 만들지 않음, 큰 구성원부터 시작),
- 틱 시간의 5% 이상을 쓰는 시스템이 쿼리 루프 안에서 상대마다 읽는 필드를, 같은 접근 서명의 다른 필드와 떼어 따로 묶습니다(그 루프가 그 필드만 훑도록; 예: 슈터의 `Ship { Pos, Hp }` → `{ Pos }`, `{ Hp }`).
- **필드별 접근 횟수**: `sijoc build --profile-fields`로 만든 프로그램은 엔티티 필드에 닿을 때마다(자기 행·쿼리 커서·핸들, 읽기와 쓰기) 스레드별 카운터를 올리고 `--profile FILE`에 `field Ship.Pos count 15160533`처럼 씁니다(보통 빌드에는 카운터가 없음). 이 프로파일로 만들면 같은 접근 서명으로 한 레코드에 묶인 필드 중 가장 바쁜 필드의 1/8보다 적게 쓰이는 필드를 다른 레코드로 뗍니다(드물게 쓰는 필드가 바쁜 필드의 캐시 라인을 차지하지 않도록; `explain`의 `pgo: Ship: { Pos } split from { Hp } (15160533 vs 30000 accesses in the profile)`). 횟수가 있으면 위의 "쿼리 루프" 추정보다 먼저 씁니다.
모두 속도만 바꾸는 결정이라 결과는 프로파일이 있든 없든, 다른 버전의 프로그램에서 받은 프로파일이든(시스템은 이름으로 맞춤) 비트 단위로 같습니다. `sijoc explain --profile-use FILE`이 각 결정과 근거를 보여 줍니다.

## 4.9 한 틱의 정확한 실행 순서

결과는 아래 규칙만으로 정해지며 스레드 수·샤드 수·플랫폼과 무관합니다. 같은 시뮬레이션을 다른 언어로 구현해 결과를 맞춰 볼 때도 이 규칙이면 충분합니다. 검증 에이전트들이 C#·C++·Rust·Go·Java·JavaScript·Python으로 구현해 비트 단위로 같은 결과를 냈습니다(11장).

0. **틱 번호와 시간.** `Game.Start`는 첫 틱 전에 한 번 돌며 `Time.Tick == 0`입니다. 첫 틱의 시스템은 `Time.Tick == 1`을 보고, `--ticks N`은 1..N틱을 실행합니다. `dt`(= `Time.Dt`)는 float32 1/60로 고정입니다.
1. **시스템 순서.** 엔티티 클래스를 **선언 순서**대로, 각 클래스 안에서는 메서드 **정의 순서**대로 `Update`와 `async` 메서드가 시스템이 됩니다. 결국 소스에 적힌 순서이고, 여러 파일 프로젝트는 파일 경로 순으로 이어 붙인 순서입니다. 이 순서는 `sijo.toml`의 `order = ["Input", "*", "Render"]`(클래스 또는 `Mob.Think` 같은 시스템 이름, `*`는 나머지)와 클래스의 `[Order(n)]`(작은 수가 먼저, 기본 0)로 바꿀 수 있습니다. 정렬 키는 (목록에서의 자리, `[Order(n)]`, 원래 순서)이고 클라이언트 시스템도 같은 순서를 따릅니다(1.12절). 하위 클래스가 재정의한 `Update`는 하위 클래스 위치에서 별도 시스템입니다. 엔티티 시스템이 모두 끝난 뒤 `Game.Update`가 돕니다. 스테이지 스케줄링은 이 순서의 의미를 바꾸지 않습니다(충돌이 없는 시스템만 같은 스테이지에 놓임).
2. **시스템 안의 엔티티 순서.** 아키타입(클래스와 하위 클래스, 선언 순서) → 테이블의 행 순서. 새 엔티티는 테이블 끝에 붙고, 파괴는 마지막 행을 빈자리로 옮깁니다(swap-remove). 그래서 행 순서는 생성 순서와 다를 수 있지만 항상 결정론적입니다.
3. **읽기.** 자기 자신은 즉시(앞 문장의 쓰기가 보임), 다른 엔티티는 시스템 시작 시점의 값입니다. `Query` 커서로 자기 자신을 만나도(`other == this`) 그 커서는 다른 엔티티로 취급되어 시작 시점 값을 읽고, 커서를 통한 쓰기는 지연됩니다.
4. **시스템 끝의 지연 명령**은 다음 순서로 적용됩니다.
   1. 원격 필드 쓰기와 원격 메서드 호출(메시지): 발생 순서(행 순서, 한 엔티티 안에서는 프로그램 순서)대로. 메시지 본문은 적용 시점의 **현재 값**을 읽습니다(앞 명령의 결과가 보임). 메시지가 만든 새 명령은 같은 큐의 끝에서 처리됩니다.
   2. `+=`/`-=`는 더하기로 적용되고 `=`는 덮어씁니다(여러 엔티티가 `=`로 쓰면 마지막 것이 남음, 린트 L401). 그 밖의 복합 대입(`other.F *= 2`, 문자열 `+=`)은 시작 시점 값으로 계산한 결과를 `=`로 씁니다. 그래서 세 엔티티가 같은 필드에 `*= 2`를 하면 8배가 아니라 2배가 됩니다. 누적이 필요하면 `+=`를 쓰거나 대상 엔티티의 메서드를 부르세요(메시지 본문은 현재 값을 읽음). 범위 타입 필드(`int in 0..100`)는 **명령 하나를 적용할 때마다** 범위로 포화합니다. 예: 범위 [0,100], 값 80에 `+60`, `-50` 순서로 오면 100 → 50.
   3. 파괴: 요청 순서대로(중복과 이미 죽은 핸들은 무시).
   4. 컴포넌트 붙이기·떼기(`Add`/`Remove`, 4.4.1절): 명령 순서대로. 행이 같은 클래스의 다른 테이블 끝으로 옮겨지고 옛 테이블은 swap-remove됩니다. 파괴된 엔티티와 이 시스템에서 생성된 엔티티에 대한 것은 버려집니다.
   5. 생성: 대기 테이블을 본 테이블 끝에 순서대로 합칩니다. 새 엔티티는 생성한 시스템에서는 돌지 않고, **같은 틱의 뒤 시스템부터** 실행됩니다. 생성한 시스템 안에서는 `Spawn`이 돌려준 핸들이 아직 살아 있지 않아 `is` 검사가 실패하고, `Count<T>()`에도 들어가지 않습니다.
5. **코루틴.** `await NextTick()`은 다음 틱의 같은 시스템 차례에, `await Wait(t)`는 `ceil(t / dt)`틱(최소 1틱) 뒤에 이어집니다. 시간을 float로 빼지 않고 틱 수로 세므로 `Wait(1)`은 60Hz에서 정확히 60틱입니다. `await Until(c)`는 조건이 이미 참이면 기다리지 않고 바로 이어지고, 거짓이면 매 틱 그 시스템 차례에 다시 검사합니다. 코루틴은 엔티티가 생긴 뒤 그 시스템의 첫 차례에 시작합니다. 앞 시스템이 생성했으면 같은 틱, 뒤 시스템이나 `Game.Update`가 생성했으면 다음 틱입니다.
6. **틱 끝.** 서버 → 클라이언트 델타 복제, 클라이언트 시스템(같은 클래스·메서드 순서, 그다음 `Game`의 `client` 메서드), 클라이언트 RPC 전송. 클라이언트 테이블은 서버 슬롯 순서로 정렬되므로 모든 클라이언트의 그리기 목록 순서가 같습니다.

원격 쓰기 뒤에 같은 필드를 같은 시스템에서 다시 읽으면 경고 `W0201`.

샤드 프로세스에서도 이 순서는 그대로입니다. 샤드마다 자기 행만 돌리고, 지연 명령·생성·`Print`에 (시스템, 아키타입 위치, 행, 순번)이라는 샤드 수와 무관한 키를 붙여 스테이지 끝에 모아 이 순서로 적용합니다(5.7.2절).

## 4.10 쿼리 루프 단형화

`foreach (var s in Query<Ship>())`는 아키타입마다 루프를 복제하고, 루프 변수 `s`를 (아키타입, 행) **커서**로 컴파일합니다. 루프 안의 `s.Pos`는 핸들 조회 없이 `t->c0_read[row].Pos`가 됩니다 (foreach 변수가 불변이라 가능한 최적화, 1.6.2절).

## 4.11 코루틴은 ECS 상태다

`async void Run()`(1.10절)은 다음처럼 바뀝니다.

- 숨은 필드 `__Run_state`(재개 지점: 0 시작, k = k번째 await 뒤, -1 끝), `__Run_timer`, 그리고 await 시점에 범위에 있던 지역 변수마다 `__Run_<이름>` 필드. 이 필드들은 일반 필드처럼 컴포넌트 클러스터링을 거칩니다.
- 메서드는 엔티티 시스템이 되고, C 코드는 함수 첫머리의 `switch (state)`가 각 await 뒤의 레이블로 바로 뜁니다. `await Wait(t)`는 남은 틱 수(`ceil(t / dt)`, 최소 1)를 타이머에 놓고 반환하며, 매 틱 1씩 줄여 0이 되면 이어집니다(4.9절).
- 결과: 수천 개의 대기 중 코루틴이 힙 할당 없이 SoA 순회되고, 엔티티마다 병렬로 실행되며, 결정론적이고, `--save-state`와 라이브 코딩 재시작을 넘어 대기 중 상태 그대로 이어집니다(테스트: `coroutines.sijo`를 50틱에 저장·복원해도 200틱 체크섬 동일).

## 4.12 근접 질의 자동 가속 (공간 격자)

게임 코드에서 가장 흔한 O(N²) 패턴은 "주변 엔티티 찾기"입니다.

```csharp
foreach (var other in Query<Boid>())
{
    if (other == this) { continue; }
    SVec2 offset = other.Pos - Pos;              // 사용자 struct 연산자
    float distSq = offset.LengthSq;              // 사용자 속성
    if (distSq < Flock.VIEW_SQ) { ... }
}
```

`spatial` 패스는 이런 루프를 찾아 **증명**합니다.

1. 루프의 마지막 문장이 `else` 없는 `if`이고, 그 앞 문장들은 효과가 없다(`if (...) { continue; }` 또는 부수 효과 없는 지역 변수).
2. 조건의 한 항이 `D < R²`(또는 `<=`)이고, `R²`는 컴파일 타임 상수이거나 **이 엔티티의 필드로만 계산되는 값**(`Range * Range`)이다. 엔티티별 반경이면 격자를 만들 때 루프를 도는 엔티티들의 가장 큰 `R²`로 칸 크기를 정하므로, 그 필드를 루프를 도는 시스템이 쓰지 않아야 한다(쓰면 상수 상한을 함께 두라고 L402가 알려 줌).
3. `D`를 **기호적으로 계산**하면(struct 연산자·속성·생성자를 인라인하고 다항식으로 전개) 정확히 `Σ (other.P.c − this.Q.c)²`이다. 예를 들어 `(other.Pos - Pos).LengthSq`는 `(o.X−s.X)² + (o.Y−s.Y)²`로 확인됩니다. 제곱근으로 쓴 거리(`(o.Pos - Pos).Length < R`, `V.Distance(o.Pos, Pos) < Range`, `Math.Sqrt(d) < R`)도 같습니다. 제곱근은 단조이고 정확히 반올림되므로 `√D < R`인 엔티티는 칸 여유(R의 0.1%) 안에 들고, 루프는 적힌 조건을 그대로 계산합니다.
4. 루프 본문이 `this`의 위치를 바꾸지 않는다.

증명되면, 그 시스템이 시작할 때 루프가 읽는 바로 그 스냅샷으로 해시 격자(칸 크기 R보다 약간 큼)를 만들고, 루프는 이웃 칸의 엔티티만 방문합니다. **격자를 만들 때 각 행을 자기 칸 주변 9칸의 버킷에 오름차순으로 넣어 두므로**(안정 계수 정렬), 질의는 배열 한 조각이고 방문 순서가 전체 순회와 같습니다. 거리 조건을 통과하는 엔티티의 집합과 순서가 같으므로 float 누적 순서까지 같아서 **결과가 비트 단위로 동일**합니다. 해시 충돌은 후보를 늘릴 뿐(조건에서 탈락) 빠뜨리지 않습니다.

| 측정 (스레드 1개) | 격자 | 전체 순회 | 비율 | 체크섬 |
|---|---|---|---|---|
| boids 1200마리 (틱 전체: 복제 포함) | 0.81 ms | 2.41 ms | 3.0× | 동일 |
| 균일 분포 1,500 | 0.40 ms | 2.26 ms | 5.6× | 동일 |
| 균일 분포 6,000 | 1.83 ms | 41.2 ms | 22× | 동일 |
| 균일 분포 24,000 | 8.7 ms | 568 ms | 65× | 동일 |

`sijoc explain`의 `[spatial queries]`가 가속한 루프와 거절 사유(예: "the loop body may change this entity's position")를 보여 주고, `-DSIJO_NO_SPATIAL`로 컴파일하면 전체 순회로 돌아갑니다(테스트가 두 빌드의 체크섬을 비교). 시스템 본문의 루프뿐 아니라 시스템이 `this`에 대해 부르는 메서드(헬퍼) 안의 루프도 가속합니다. 그 헬퍼에 닿는 시스템마다 시작할 때 격자를 만들고 끝날 때 버리므로, 같은 헬퍼가 시스템 밖에서 실행되면(시스템 뒤에 적용되는 메시지, 그 격자를 만들지 않는 다른 시스템) 전체 순회로 돌아갑니다. 8192행 이상이면 격자를 여러 스레드가 만듭니다(결과는 직렬과 같음). 한계: 반경이 상대 엔티티의 값에 따라 달라지면(`o.Range`) 상수 상한을 함께 써야 가속되고(L402), 엔티티 64개 미만이면 전체 순회.

## 4.13 격자 연산의 병렬화 (`Grid<T>`)

가루·물·열처럼 칸마다 상태가 있는 시뮬레이션은 엔티티가 아니라 격자(2·3차원 배열) 위의 루프입니다. 손으로 쓴 `for (y) for (x)` 루프는 앞에서 쓴 칸을 뒤에서 읽어(Gauss-Seidel) 순서에 결과가 달려 있어 병렬화할 수 없습니다. `Step`·`Move`(1.14.2절)는 엔티티 시스템과 같은 규칙을 칸에 줍니다: **다른 칸은 연산 전의 값으로 읽힌다.** 그러면 칸들을 어떤 순서로든, 여러 스레드에서 계산해도 결과가 비트 단위로 같습니다.

컴파일러는 람다를 보고 실행 방식을 정합니다(`src/grid.rs`).

| 판정 | 조건 | 실행 |
|---|---|---|
| 맵 | 람다가 격자를 `c`(자기 칸)로만 읽음 | 제자리에 씀(버퍼 없음) |
| 스텐실 | `g[x + i, y + j]`·`g.Get(x + i, y + j, f)`처럼 상수 오프셋으로 읽음 | 두 번째 버퍼에 쓰고 바꿔 끼움. 각 축에서 가장 큰 오프셋 r보다 가장자리에서 먼 칸(내부)은 그 읽기의 경계 검사·`Get`의 범위 비교 없이, 가장자리 칸만 검사하며 계산(가장 안쪽 축은 가장자리·내부·가장자리 세 구간으로 나눠 칸마다 분기 없음) |
| 일반 읽기 | 계산한 좌표로 읽음 | 그 읽기는 검사를 유지 |
| 이동 | `Move` | 각 칸의 결과를 이전 격자만으로 계산: 빈 칸은 자기에게 오려는 이웃 중 정해진 순서의 첫 칸을 받고, 찬 칸은 자기가 가려는 빈 칸이 자기를 고를 때 비움. 이웃의 제안은 필요한 곳에서 다시 계산(람다는 효과가 없으므로) |

- 칸이 `SIJO_GRID_PAR_MIN`(4096)개 이상이고 이미 병렬 영역 안이 아니면(격자를 가진 엔티티가 많아 시스템이 엔티티 단위로 병렬이면 그쪽이 병렬) 바깥 축을 스레드 수로 나눠 돕니다. 스레드마다 자기 패닉을 잡는 방식은 병렬 시스템과 같습니다.
- 람다 안의 `Random`은 칸 번호로 키를 정하므로 스레드 수와 무관합니다. 연산 하나가 엔티티의 난수 흐름에서 키를 하나 뽑으므로 같은 연산을 한 틱에 여러 번 해도 매번 다릅니다.
- 테스트(`tests/grid.rs`): `Move`·`Step`의 결과를 같은 규칙으로 손으로 쓴 루프와 300틱 동안 칸마다 비교(차이 0), 스레드 1/4, ASan/UBSan, wasm 빌드와 네이티브 빌드의 체크섬 동일.
- 측정(1024x1024 int 열 확산, 이 VM): 손으로 쓴 이중 버퍼 루프 2.5 ms, `Step`(경계 검사 없는 내부) 2.2 ms, `Get`을 쓴 같은 스텐실 2.0 ms. 칸마다 일이 많으면(삼각 함수 3개) 1스레드 10.3 ms → 4스레드 4.4 ms. 단순한 스텐실은 메모리 대역폭에 묶여 스레드를 늘려도 거의 같습니다.
- 아직 없는 것(8.3절): 격자를 청크로 나눠 샤드마다 맡기기와 헤일로, 청크 단위 더티 표시로 복제 줄이기(지금은 다차원 배열의 원소 단위 델타), 엔티티 ↔ 칸 색인(지금은 `Grid<Ship?>`처럼 핸들 격자를 직접 둠).
