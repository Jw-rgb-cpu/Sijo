# 8. 구현 현황과 로드맵

`compiler/`의 `sijoc`는 설계의 핵심 가설 — "컴파일러가 전체 프로그램을 알면 사람이 하던 ECS 분해·병렬화·복제·메모리 배치를 대신할 수 있다" — 을 검증하는 프로토타입이며, 이 문서는 버전 0.1.1 기준입니다. 언어, 컴파일러 지능(값 범위·e-graph·PGO), 실제 네트워크와 샤드 프로세스까지 동작합니다. Rust(외부 의존성 0, 약 3.9만 줄)로 작성되었고 C11(GNU)을 생성해 gcc/clang으로 네이티브 실행 파일을 만듭니다.

## 8.3 로드맵

구현된 기능은 8.1절 표에 있습니다. 여기에는 남은 일만 적습니다.

### 언어
- 엔티티와 무관하게 떼어 내는 코루틴(Verse의 `spawn`)

### 격자 (1.14.2절, 4.13절)
- 청크 단위 분할: 큰 격자를 청크로 나눠 샤드마다 맡기고, 스텐실 반경(`[grids]`가 이미 계산함)만큼의 헤일로를 이웃 샤드와 교환
- 청크 단위 더티 표시로 복제 줄이기(지금은 다차원 배열의 원소 단위 델타)
- 엔티티 ↔ 칸 색인: 엔티티의 `[Spatial]` 위치로 칸을 찾고 칸의 엔티티를 도는 질의(지금은 핸들 격자 `Grid<Ship?>`를 직접 둠)
- 순서가 결과인 알고리즘을 내장 함수로 더: 경로 찾기(BFS 거리장), 연결 요소 번호 매기기

### 컴파일러 지능
- e-graph 값 범위가 고정 길이 배열 필드의 길이를 알아 `Cells[i % N]` 같은 계산한 첨자도 증명(지금은 `i < N` 카운터만)
- GPU 오프로딩의 다음 단계: 실제 GPU에서의 비트 동일성 확인, 장치에 열을 계속 두기(7.4절). 어느 시스템을 장치에서 돌릴지는 지금처럼 컴파일 때의 판정과 행 수(`SIJO_GPU_MIN`)로만 정함

### 분산
- 코디네이터(샤드 0) 복구
- 게이트웨이 여러 개: 클라이언트는 접속할 때 게이트웨이 하나에 정해지고(예: 클라이언트 번호로) 시야(`Net.View`)가 바뀌어도 옮기지 않음
- 샤드가 주인인 행만 저장하는 메모리 분할(지금은 모든 샤드가 모든 행의 자리를 가짐)
- 2차원 분할(지금은 X 슬랩): 지금처럼 모든 샤드가 같은 위치 표본으로 같은 경계(가중 분위수)를 계산하고, 엔티티는 자기 위치가 든 영역의 샤드가 맡음
- 명령 적용의 분할: 메시지 본문이 다른 엔티티를 읽지 않으면 그 명령을 대상의 주인 샤드에만 보내 그 샤드만 적용(지금처럼 응답 없는 단방향 명령). 지금은 모든 샤드가 모든 명령을 적용
- 엔디언이 다른 기계 사이의 샤드(지금은 명령 데이터가 그 기계의 바이트 순서)

### 네트워크
- 렌더링 속도의 클라이언트 보간: 클라이언트가 받은 앞뒤 스냅샷 사이를 렌더 프레임마다 보간(지금은 잃어버린 틱만 두 스냅샷 사이로 보간)
- 플레이어별 인증: 지금의 `--key`는 모든 피어가 나눠 쓰는 사전 공유 키라 플레이어마다 접속 권한을 주고 뺄 수 없음. 후보는 클라이언트가 만든 키 쌍의 공개키를 서버가 허용 목록으로 확인하는 방식, 또는 접속을 받아들일지 게임 코드가 정하는 훅
- 큰 스냅샷의 손실: 조각 하나를 잃으면 그 스냅샷 전체를 쓸 수 없음(지금은 손실률이 2% 이상일 때 패리티 조각 하나로 잃은 조각 하나를 복원). 스냅샷을 통째로 적용하는 지금의 기준선 규칙(5.5.2)은 그대로 두고, 후보는 패리티 조각을 늘리는 것. 예산을 둘 때 확인 전의 변경이 스냅샷마다 다시 실리는 비용은 방식을 정하지 않음
- 조합이 바뀐 엔티티의 복제 값을 전체 대신 바뀐 것만 보내기

### 개발자 경험
- 프로세스 재시작 없는 핫 패치: 인터프리터/Cranelift 개발 백엔드로 재컴파일 지연을 수십 ms로
- C 대신 LLVM IR/MLIR 직접 생성, MSVC 지원 (Windows는 MinGW로 지원, 생성 C는 GNU C 문장식 사용)

## 8.4 알려진 제약

- 생성 C는 GNU 확장(문장식 `({ ... })`)을 사용 → gcc/clang 필요
- wasm32: 한 스레드(OpenMP 없음), 네트워크 없음(게임 자신의 클라이언트는 프로세스 안), 호스트 함수가 던진 JS 예외는 게임을 정리하지 않고 그대로 올라감
- 격자: `Move`는 이웃 한 칸(각 축 -1..1)까지, 진 칸은 그 틱에 다른 곳을 시도하지 않음, 람다 본문은 식 하나(`{ return 식; }`)
- 샤딩: 모든 샤드가 모든 행의 자리를 가짐(메모리는 나누지 않음), 록스텝이라 배리어마다 샤드 간 지연, 코디네이터(샤드 0)는 복구하지 않음, 분할은 X 슬랩만, 모든 샤드가 모든 명령을 적용, 전역 시스템이 모든 엔티티를 읽으면 바뀐 값이 매 틱 코디네이터로 감, 샤드 프로세스들은 엔디언이 같아야 함(5.7.10)
- 네트워크: 렌더 보간·플레이어별 인증 없음(`--key`는 사전 공유 키), 대역폭 예산(`--budget`)은 확인 전 변경을 매번 다시 실어 왕복이 길면 새 변경의 자리가 줄어듦, 예측은 복제 상태만 읽고 자기 엔티티만 바꾸는 RPC에 한함, 복제되는 리스트는 매 틱 다시 직렬화해 비교(비용은 크기에 비례)하고 원소 델타는 같은 위치·이동한 구간의 복사만 찾음(정렬처럼 대부분이 바뀌면 전체 전송), 복제되는 컬렉션의 엔티티 참조는 nullable이어야 함(E0606), 스냅샷 16MB 이하, 33틱 이상 연속으로 잃어버린 구간의 클라이언트 프레임은 건너뜀
- 델리게이트는 서버 코드에만(클라이언트 코드·원격 메시지·RPC 인자·컴포넌트 필드에는 없음), 멀티캐스트·`==` 없음, 인터페이스의 `static virtual` 없음, 배열은 3차원까지(`T[,,]`). 오버로딩은 매개변수 타입으로만(선택적 매개변수·`params` 없음), 같은 제네릭 인터페이스의 두 인스턴스는 매개변수까지 같은 메서드가 없을 때만 한 클래스가 구현함. C#과 다른 점은 11.6절
- 최대 64개 아키타입(제네릭 엔티티 클래스의 인스턴스와 컴포넌트 조합 포함). 원격 메시지 인자는 값·문자열·리스트·배열(복사본, 한 메시지에 합쳐 64KB까지)이고 사전과 `ref`/`out`은 안 됨(E0248). 클라이언트 RPC 인자는 값과 문자열만(E0608)
- 컴포넌트: 16조합을 넘는 클래스는 열린 테이블 하나(컴포넌트 종류 32개까지, E0266; 없는 컴포넌트의 열도 자리를 차지하고 컴포넌트 시스템은 클래스의 모든 행을 훑음, 행 순서로 방문), 컴포넌트 필드에 사전·델리게이트 없음(E0264, 문자열·리스트·배열은 `Add`가 복사해 실음, 64KB까지), 가상·제네릭 컴포넌트 메서드 없음, 컴포넌트는 필드·매개변수·컬렉션에 담을 수 없음(E0263: 엔티티 핸들을 담고 `Get`), 조합이 바뀐 엔티티는 복제 값 전체를 한 번 다시 보냄, 테이블마다의 연산(테이블 조작·코덱·상태 파일)과 메서드 밖 쿼리 루프는 조합 테이블마다 생성됨
- 제네릭 엔티티 클래스: 상수·`extern` 메서드를 둘 수 없음(E0258, 상수는 제네릭 정적 클래스에), 쓰이지 않는 제네릭 코드의 본문은 타입 매개변수를 모르는 채로 검사(`T`에 대한 연산은 인스턴스가 생길 때), 인스턴스마다 아키타입이 하나씩 생겨 64개 한도에 들어감, 호버는 멤버를 첫 인스턴스로 보여 줌
- 범위 타입: struct 멤버(그 struct를 담는 엔티티 필드에 범위를 두면 모든 멤버에 적용), 컬렉션 원소(`List<int in 0..9>`), 상수, `ref`/`out` 매개변수에는 쓸 수 없고, 지역 변수·매개변수·반환 타입은 int·float만. 경계의 상수는 숫자와 다른 상수로 계산되어야 함(함수 호출 불가)
- 그 자리에서 선언한 `out int v`는 불변(바꾸려면 `mut int v;`를 먼저 선언), async 메서드는 `own` 매개변수를 받지 못함
