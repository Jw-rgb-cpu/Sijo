# 5. 자동 네트워크와 분산 부하

Verse처럼 **게임 코드에는 네트워크 코드가 없습니다.** 서버 권한(server-authoritative) 모델에서 컴파일러가 무엇을, 얼마나 작게, 언제 보낼지 결정합니다.

## 5.1 실행 컨텍스트

```
           ┌──────────── 서버 (권한) ─────────────┐   UDP    ┌──── 클라이언트 (여러 개) ────┐
 입력 RPC ─▶ Update 시스템들 → 지연 명령 적용 → 프레임 ──델타──▶ 디코드 → client 시스템
           └──────────────────────────────────────┘ ◀─ack·RPC─ └──────────────────────────────┘
```

- 기본 컨텍스트는 서버. `client` 수식어가 붙은 메서드(`public client void Render()`)는 클라이언트 월드에서 실행됩니다.
- 클라이언트 코드는 시뮬레이션 상태를 쓸 수 없습니다(`E0601`) — 치트 방지가 타입 시스템 수준에서 보장됩니다.
- 생성된 실행 파일 하나가 서버 프로세스, 클라이언트 프로세스, 둘을 한 프로세스에 묶은 모드로 실행됩니다 (5.5.1).

## 5.2 복제 추론 (Replication Inference)

> **필드 f는 클라이언트 컨텍스트 코드가 (전이적으로) 읽으면 복제된다.**

- `Render()`가 `Pos`와 `Hp`만 읽으면 `Vel`, `Cooldown`, `Kills`는 **전송되지 않습니다**. 수동 주석 없이도 대역폭 최소화.
- `[Replicated]` / `[NotReplicated]`로 덮어쓸 수 있습니다 (예: 예측을 위해 `Vel`을 강제 복제).
- `mut`이 없는 필드는 생성 뒤에 바뀌지 않으므로, 생성할 때 보낸 뒤로는 그 필드 때문에 델타가 생기지 않습니다.
- 복제되는 필드끼리 같은 컴포넌트로 묶이도록 클러스터링 서명에 "복제됨"이 포함됩니다 → 직렬화가 연속 메모리를 훑습니다.

## 5.3 범위 분석 기반 양자화

Netcode for Entities는 `[GhostField(Quantization=100)]`을 사람에게 요구합니다. Sijo는 비트 수를 **값의 범위**에서 계산합니다.

1. **선언된 계약** 범위 타입 `public mut int in 0..100 Hp` → 모든 쓰기 지점(자기 쓰기, 원격 명령 적용, 초기화)에 포화 연산을 삽입 → 범위가 *항상 참* → `ceil(log2(101)) = 7비트`.
2. **추론된 범위**: 필드의 모든 쓰기가 상수이거나 `Math.Clamp(e, a, b)` 형태면 범위를 자동 추론 → 계약 없이도 양자화.
3. float: `[Precision(0.01)] public mut float in -512..512 X` → `ceil(log2(1024/0.01 + 1)) = 17비트`. 범위가 없으면 32비트 원본. 정밀도가 범위를 나누어떨어지지 않으면 맨 위 단계는 `hi`로 복원됩니다(`[Precision(0.4)] float in 0..1`은 0, 0.4, 0.8, 1): 클라이언트가 보는 값도 언제나 범위 안입니다.
4. struct(예: `SVec2`) 필드는 멤버별로 같은 규칙을 적용합니다. `[Precision(0.01)] public mut SVec2 in 0..64 Pos`는 `X`, `Y`가 각각 13비트입니다.
5. 엔티티 참조(`Ship? Target`)는 32비트: 서버 슬롯 번호와 세대의 하위 8비트입니다. null, 이미 파괴된 엔티티, 클라이언트에 존재하지 않는(복제되지 않는 아키타입의) 엔티티는 0입니다. 클라이언트는 스냅샷 전체를 적용한 **뒤에** 서버 슬롯을 자기 핸들로 바꾸므로, 같은 스냅샷에서 생긴 엔티티를 가리켜도 됩니다. 대상이 아직 없거나 세대가 맞지 않으면 null이 됩니다(5.5.4의 해시도 이 규칙으로 계산).
6. 문자열은 서버가 값마다 붙이는 **번호**로 프레임에 들어갑니다(같은 내용이면 같은 번호, 번호는 다시 쓰지 않음, `""`은 0). 그래서 "바뀌었는가"는 다른 값처럼 정확한 비교이고, 스냅샷이 그 잎을 보낼 때(생성, 또는 그 컴포넌트가 바뀌었을 때)만 번호와 함께 UTF-8 바이트를 보냅니다(긴 문자열이 조금 바뀌면 확인된 값에 대한 델타만, 5.5.3). 복제되는 문자열 필드는 혼자 한 컴포넌트가 되므로 다른 필드가 바뀌어도 다시 보내지 않습니다. 클라이언트는 번호 → 글자 표를 두고, 양쪽 모두 64틱마다 프레임 기록이 더는 가리키지 않는 번호를 버립니다(실행 요약의 `replicated strings`). 해시는 글자 내용으로 계산합니다.
7. 리스트·배열·사전(숫자·bool·`char`·enum·문자열·엔티티 참조, 그것들의 struct, 다른 리스트를 담은 것)은 원소 수(다차원 배열은 차원마다 길이)와 원소들을 정해진 바이트 형식(32비트 리틀 엔디언 숫자, 1바이트 bool, 길이가 앞에 붙은 문자열, 엔티티 참조는 5번과 같은 32비트 서버 값, 중첩 리스트도 같은 방식)으로 이어 붙인 값을 문자열과 같은 표에 넣어 번호로 보냅니다. 사전은 키·값 쌍을 사전 자신의 순서(삽입 순서, `Remove`는 마지막 쌍을 빈자리로 옮김)대로 담은 리스트이고, 클라이언트는 받은 쌍으로 색인을 다시 만듭니다. 리스트는 `Add`·원소 쓰기처럼 제자리에서도 바뀌므로 복제되는 리스트 필드(혼자 한 컴포넌트)는 매 틱 다시 직렬화해 비교합니다(비용은 리스트 크기에 비례). 내용이 바뀐 틱에만 보내며, 클라이언트가 확인한 값에 대한 **원소 단위 델타**(바뀐 바이트 구간, 덧붙인 꼬리, 새 길이)가 바이트 전체보다 작으면 델타를 보냅니다(5.5.3). 그래서 큰 리스트의 원소 몇 개가 바뀌면 그 원소만큼만 갑니다.
8. 엔티티 참조를 담은 컬렉션(`List<Ship?>`, `Ship?[]`, 참조를 담은 struct의 리스트, `List<List<Ship?>>`, `Dictionary<Ship?, int>`, `Dictionary<string, Ship?>`)은 원소마다 5번의 서버 값(슬롯 + 세대 하위 8비트)을 담습니다. 클라이언트는 스냅샷 전체를 적용한 **뒤에** 원소마다 자기 핸들로 바꾸고(5번과 같은 규칙: 대상이 파괴되었거나 클라이언트에 없으면 null), 엔티티가 생기거나 없어진 프레임마다 그 바이트에서 다시 맞춥니다. 그래서 시야(5.8) 밖으로 나간 대상은 null로 읽히고 다시 들어오면 이어집니다. 참조가 키인 사전에서는 클라이언트가 갖지 못한 키의 쌍이 빠집니다(null 키가 둘일 수는 없으므로). 해시(5.5.4)와 복제 확인도 같은 규칙으로, 그 클라이언트가 보는 대상만 남겨 계산합니다. 클라이언트가 어떤 대상이든 못 볼 수 있으므로 복제되는 컬렉션의 참조는 nullable이어야 합니다: 클라이언트 코드가 `List<List<Ship>>` 필드를 읽으면 `E0606`이고, 노트가 `List<List<Ship?>>`로 선언하라고 알려 줍니다. 클라이언트 프레임마다 참조를 다시 맞추는 비용은 그 컬렉션 크기에 비례하며, 엔티티 집합도 컬렉션도 그대로인 프레임에서는 건너뜁니다.

양자화는 결정론적이며, 서버도 클라이언트가 볼 값(양자화된 값)을 기준으로 변경 여부를 판단합니다 (Iris가 "양자화된 상태 사본"을 유지하는 것과 같은 방식).

## 5.4 변경 추적 — 폴링 없음

Iris는 "복제 시스템은 폴링하지 않고, 변경을 통지받는다"는 원칙을 씁니다. Sijo는 **컴파일러가 모든 쓰기 지점을 알기 때문에** 통지 코드를 자동 삽입합니다.

```c
// Hp -= 10 (원격 명령 적용 시) →
c->Hp = sijo_clamp_i32(c->Hp - 10, 0, 100);
t->dirty_c0[row] = 1;                 // 컴파일러가 삽입한 더티 플래그
```

네트워크 단계에서는 더티인 행만 다시 양자화해 틱마다 **프레임**(양자화된 복제 상태)을 만들고, 각 클라이언트가 확인(ack)한 프레임과 비교해 바뀐 컴포넌트만 보냅니다 (5.5.2).

## 5.5 스냅샷과 실제 전송

### 5.5.1 실행 방식

| 실행 | 하는 일 |
|---|---|
| `prog` (기본) | 서버 월드와 클라이언트 월드를 한 프로세스에서 실행하고 메모리 안의 데이터그램 링크로 연결합니다. 실제 UDP와 **같은 프로토콜 코드**를 거칩니다. 손실이 없으면 클라이언트의 RPC가 바로 다음 틱에 도착하므로 실행 결과가 비트 단위로 결정론적입니다. |
| `prog --server PORT` | 서버 월드만 실행합니다. UDP로 클라이언트를 몇 개든 받습니다(`--max-clients`, 기본 256). `PORT`가 0이면 빈 포트를 골라 출력합니다. 소켓은 IPv6 듀얼 스택(IPv4 클라이언트도 받음)이며, IPv6을 쓸 수 없는 시스템에서는 IPv4로 엽니다. |
| `prog --connect HOST:PORT` | 클라이언트 월드만 실행합니다. 스냅샷을 받아 적용하고, 적용한 스냅샷마다 `client` 시스템을 한 번 돌리고, ack와 RPC를 보냅니다. `HOST`는 이름, IPv4, 또는 `[::1]:7777`처럼 대괄호로 감싼 IPv6 주소입니다. |

어느 방식이든 `--sim-loss P --sim-latency-ms MS --sim-jitter-ms MS --sim-dup P --sim-seed S`를 주면 그 프로세스가 보내는 데이터그램마다 손실·지연·지터(→ 순서 뒤바뀜)·중복을 시뮬레이션합니다. 시드를 고정한 PRNG를 쓰므로 재현됩니다. 한 프로세스 모드는 가상 시간을 쓰므로 손실이 있어도 실행 결과 전체가 결정론적입니다.

**서버 시뮬레이션은 네트워크와 무관합니다.** 네트워크는 틱 사이에만 동작하고, 서버 월드에 들어가는 것은 클라이언트 RPC뿐입니다. RPC가 없는 boids는 `--server` 실행, 손실이 있는 실행, 한 프로세스 실행의 월드 체크섬과 복제 상태 해시가 모두 같습니다(테스트로 확인). `--tick-rate HZ`는 실시간 속도만 바꾸고 시뮬레이션 dt(1/60초)는 그대로 둡니다.

### 5.5.2 프레임과 확인된 기준선 (Quake 3 / Iris 방식)

1. 서버는 매 틱 끝에 복제되는 엔티티의 양자화된 상태를 **프레임**으로 캡처합니다. 프레임은 서버 슬롯 순으로 정렬되고, 엔티티마다 세대·아키타입·양자화 값을 담습니다. 더티 플래그가 선 컴포넌트만 다시 양자화합니다.
2. 최근 64틱(60Hz에서 약 1초)의 프레임을 링 버퍼에 보관합니다. 시야(`Net.View`, 5.8)도 대역폭 예산(`--budget`, 5.8.1)도 없으면 모든 클라이언트가 같은 세계를 보므로 이 링을 **클라이언트들이 공유**합니다. 메모리는 O(기록 길이 × 엔티티 수)이고 클라이언트 수와 무관합니다. 클라이언트별로 따로 두는 것은 "어느 프레임까지 확인했는가"(ack)와 연결 상태뿐이며, 같은 기준선을 가진 클라이언트들은 인코딩 결과도 함께 씁니다. 시야나 예산이 있는 클라이언트는 그 클라이언트가 받은 엔티티 집합·프레임을 따로 기록합니다(5.8).
3. 클라이언트에게 보내는 스냅샷은 **그 클라이언트가 확인한 가장 새 프레임**에 대한 델타입니다. 확인한 프레임이 없거나 ack가 기록보다 오래되면 전체 상태를 보냅니다. 늦게 들어온 클라이언트도 이 경로로 전체 상태를 받습니다. 생성·파괴도 그 기준선에 대한 상대값이라, 잃어버린 스냅샷에 있던 생성은 확인될 때까지 다음 스냅샷에 다시 들어갑니다. 재전송 큐가 따로 없고, 잃어버린 정보는 항상 최신 값으로 다시 보내집니다.
4. 클라이언트도 적용한 프레임을 같은 크기의 링에 보관해 기준선으로 씁니다. 스냅샷을 디코드(기준선 + 델타 = 새 프레임)한 뒤 직전에 적용한 프레임과 비교해 클라이언트 월드에 생성·파괴·변경을 적용합니다. 서버 슬롯 순서로 적용하므로 클라이언트 쪽 슬롯 할당도 결정론적입니다. 이미 적용한 틱보다 오래된 스냅샷(순서 뒤바뀜)과 중복은 버리고, 가장 새로 적용한 틱을 매 패킷에 ack합니다. 서버는 ack를 최댓값으로만 갱신하므로 늦게 온 패킷이 기준선을 되돌리지 못합니다.
5. 안전장치: 클라이언트가 기준선이 없어 디코드할 수 없는 스냅샷을 계속 받으면 *재동기화 에포크*를 올리고, 서버는 그 클라이언트에게 전체 상태를 다시 보냅니다.

### 5.5.3 와이어 포맷

스냅샷 본문 (비트 패킹, 슬롯 번호 오름차순):

```
레코드* 끝
레코드 = [태그 2b] [슬롯 번호 차이 varint] 본문
  1 파괴   (기준선에 있던 엔티티)
  2 생성   [세대 varint] [아키타입 번호] [모든 잎의 양자화 값]   (같은 슬롯의 기준선 엔티티는 대체)
  3 갱신   [컴포넌트 변경 마스크] [바뀐 컴포넌트의 양자화 값]
끝 = 태그 0
```

- 값은 양자화 비트 수만큼 정확히 비트 패킹하고, 슬롯 번호와 세대는 가변 길이로 씁니다.
- 생성 시 기준선은 0입니다(Netcode for Entities와 같은 결정). 기본값과 같은 필드가 많을수록 유리합니다.
- 런타임은 "순진한 전송(모든 복제 필드를 32비트로 매 틱)" 대비 압축률을 보고합니다.

**문자열·리스트 잎과 원소 단위 델타.** 문자열·리스트(배열·사전 포함) 잎은 표의 번호와 바이트로 갑니다. 갱신 레코드에서는 같은 잎이 기준선(클라이언트가 확인한 프레임)에도 있으므로, 서버는 기준선 값의 바이트를 새 바이트로 바꾸는 연산 목록을 만들어 그것이 바이트 전체보다 작을 때 보냅니다.

```
잎   = [번호 varint]                                    번호 0: "" (그 뒤 없음)
       ( [길이 n > 0 varint] [바이트 n개]                   전체
       | [0]                                               기준선과 같은 값 (같은 컴포넌트의 다른 잎이 바뀜)
       | [0] [새 길이 varint] 연산* )                      기준선 값에 대한 델타 (연산은 새 길이를 채울 때까지)
연산 = [len << 1 | 1 varint] [이동 zigzag varint]          기준선의 (현재 위치 + 이동)에서 len바이트 복사
     | [len << 1 varint] [바이트 len개]                    새 바이트 len개
```

- 인코더는 앞에서부터 욕심껏 가장 긴 복사를 고릅니다. 후보는 직전 복사와 같은 이동, 같은 위치(이동 0), 다음 4바이트가 기준선에서 마지막으로 나온 곳입니다. 4바이트보다 짧은 일치는 새 바이트로 둡니다. 그래서 원소 몇 개 쓰기(같은 위치 복사 사이에 바뀐 원소만), 끝에 덧붙이기(복사 하나 + 꼬리), 길이 줄이기(새 길이 + 복사 하나), 맨 앞을 빼고 끝에 넣는 미끄럼 창(이동 +4인 복사 하나 + 새 원소), 중간 삽입·삭제(앞부분 복사 + 이동한 뒷부분 복사)가 모두 몇 바이트입니다. 원소 수(앞 4바이트)가 바뀌면 바뀐 바이트만 새 바이트로 갑니다. 새 값이 8바이트보다 짧거나 기준선 값이 `""`이면 언제나 전체로 갑니다.
- 기준선은 5.5.2의 그 기준선이므로 규칙이 그대로 성립합니다: 클라이언트는 확인한 프레임과 그 프레임이 가리키는 모든 문자열·리스트 값을 아직 가지고 있습니다(양쪽 표의 GC가 기록 안의 모든 프레임을 표시). 손실·중복·순서 뒤바뀜, 늦게 들어온 클라이언트(생성 레코드는 언제나 전체), 시야(그 클라이언트가 그 틱에 받은 집합이 기준선), 대역폭 예산(클라이언트별 프레임이 기준선이고, 비용도 델타 크기로 셈)에서 모두 같습니다. 디코더는 기준선 값이 없거나 연산이 어느 쪽 범위든 벗어나면 스냅샷 전체를 버립니다(입력 검증).
- 인코딩은 바이트만으로 정해지므로(해시도 바이트 단위 정수 연산) 어느 플랫폼의 서버든 같은 스냅샷을 만듭니다. 비교용으로 서버의 `--no-list-deltas`는 바뀐 값을 원소 델타 없이 전체로 보냅니다.
- 실행 요약: `strings and lists: N sent whole, M as deltas against the acknowledged value (D bytes instead of W)`.
- 예: `tests/programs/biglists.sijo`(엔티티 6개: 틱마다 두 칸을 쓰는 512칸 리스트, 200개 미끄럼 창, 100~300개 사이를 오가는 로그, 길어졌다 잘리는 문자열, 참조 240개, 가끔 정렬)를 300틱 돌리면 프로세스 안에서 25,343 → 566 B/tick(45배), 양방향 손실 20%·지연 30±10ms UDP(클라이언트 3개, 하나는 중간 참여)에서 클라이언트당 약 23 KB/tick → 1.9 KB/tick입니다. 끝의 복제 상태 해시는 어느 쪽이든 같습니다.

데이터그램 (모두 1192바이트 이하, `--key`로 봉인하면 1232바이트 이하 — IPv6의 최소 MTU 1280에서 IP·UDP 헤더 48바이트를 뺀 값이라 어느 경로에서도 IP 조각화가 없음; 리틀 엔디언, 공통 헤더 = 종류 u8 · 세션 u32 · 데이터그램 번호 u16):

| 종류 | 방향 | 내용 |
|---|---|---|
| CONNECT | C→S | 클라이언트 난수, `"SIJO"`, **프로토콜 해시**(복제 계획·양자화·RPC 표에서 계산 — 다른 프로그램이나 다른 컴파일 결과끼리는 연결하지 않음) |
| ACCEPT / REJECT | S→C | 세션 토큰·클라이언트 번호·틱 속도·시드·현재 틱 / 거부 이유(프로토콜, 만원, 게임 종료) |
| SNAP | S→C | 틱, 기준선 틱, RPC ack, 조각 번호/조각 수, 본문 조각 (헤더 23바이트, 조각 ≤ 1169바이트) |
| CLIENT | C→S | ack한 틱, 재동기화 에포크, 최근 손실률, 첫 RPC 번호, RPC 레코드들 |
| DISCONNECT · BYE · BYE_ACK | | 연결 종료, 게임 종료 인사와 그 확인 |

- **조각화**: 1169바이트보다 큰 스냅샷은 조각으로 나눠 보내고 (틱, 기준선, 조각 수)로 재조립합니다. 1200마리 boids의 델타는 약 4.2KB(4~5조각), 전체 상태는 약 11KB(10조각)입니다. 동시에 8개 스냅샷까지 조립하고, 더 새 스냅샷이 적용되면 미완성 조립은 버립니다.
- **패리티 조각(FEC)**: 조각 난 스냅샷은 조각 하나만 잃어도 쓸 수 없습니다(20% 손실에서 6조각이 모두 도착할 확률은 26%). 클라이언트가 보고한 최근 손실률이 2% 이상이면 서버는 모든 조각의 XOR인 패리티 조각 하나를 덧붙이고, 클라이언트는 잃어버린 조각 하나를 복원합니다. 본문은 끝 레코드로 끝나므로 복원된 마지막 조각의 0 채움은 무시됩니다. 20% 손실 boids에서 적용된 스냅샷이 2.5배로 늘고 기준선이 젊어져 델타도 작아집니다(대역폭 +9%). 손실이 없으면 보내지 않습니다.
- **핸드셰이크**: 클라이언트는 응답이 올 때까지 100ms마다 CONNECT를 보내고, 서버는 같은 난수의 CONNECT에 같은 ACCEPT를 다시 보냅니다(ACCEPT 손실 대비). 스냅샷은 클라이언트의 첫 패킷으로 세션이 확인된 뒤부터 보냅니다.
- **연결 관리**: `--timeout-ms`(기본 5초) 동안 아무것도 받지 못한 상대는 끊습니다. 클라이언트는 Ctrl-C를 받으면 DISCONNECT를 보내고, 서버는 Ctrl-C를 받으면 정상 종료 절차(5.5.4)를 밟습니다. 같은 주소에서 새 난수로 CONNECT가 오면(같은 주소에서 재시작한 클라이언트일 수도, 그 주소를 위조한 누군가일 수도 있음) 새 세션을 받아들이되 **확인될 때까지 기존 연결을 유지**합니다. 새 세션이 ACCEPT의 세션 토큰을 담은 첫 CLIENT 패킷을 보내 그 주소에서 받을 수 있음을 증명하면 그때 이전 연결을 정리합니다. 확인되지 않은 세션은 스냅샷을 받지 못하고 시간이 지나면 끊기며, 다음 CONNECT가 오면 대체됩니다.
- **메모리 상한**: 서버는 프레임 64개와 클라이언트별 고정 크기 상태를, 클라이언트는 프레임 64개, 조립 슬롯 8개, RPC 큐(4096개 상한)를 씁니다. 지연 시뮬레이션 큐도 16384 데이터그램이 상한입니다. 오래 실행해도 메모리가 늘지 않습니다.
- **암호화** (`--key HEX`, 또는 환경 변수 `SIJO_KEY`): 서버와 클라이언트가 같은 32바이트 키(16진수 64자리)를 가지면 모든 데이터그램을 XChaCha20-Poly1305로 봉인합니다. 7바이트 헤더는 라우팅을 위해 평문이지만 인증되고(AAD), 나머지는 암호화되며, 무작위 24바이트 nonce와 16바이트 태그가 붙습니다(+40바이트). 모든 피어가 키 하나를 나눠 쓰지만 192비트 무작위 nonce는 사실상 겹치지 않으므로 송신자끼리 카운터를 맞출 필요가 없습니다. 인증에 실패한 데이터그램은 버리고 셉니다(요약의 `encryption` 줄). 그래서 키가 없는 사람은 접속하지도, 패킷을 끼워 넣거나 바꾸지도, 내용을 읽지도 못합니다. 재전송된 옛 데이터그램은 프로토콜이 이미 무해하게 처리합니다(오래된 스냅샷은 무시, RPC는 순번으로 중복 제거, 같은 CONNECT에는 같은 ACCEPT). 구현은 의존성 없는 C(`runtime/sijo_crypto.h`)이고, RFC 8439와 XChaCha 초안의 시험 벡터, Python `cryptography`와의 무작위 비교(빅엔디언 포함)로 확인했습니다.
- **입력 검증**: 모든 패킷은 길이를 검사하는 리더로 읽습니다. 잘못된 레코드, 범위 밖 슬롯, 복제되지 않는 아키타입이 있으면 스냅샷 전체를 버립니다. 서버와 클라이언트 모두 ASan/UBSan 아래에서 무작위 패킷과 반쯤 유효한 패킷 수천 개로 시험했습니다.

### 5.5.4 종료와 수렴 확인

`--server PORT --ticks N`은 N틱 뒤 시뮬레이션을 멈추고, 마지막 프레임을 모든 클라이언트가 ack할 때까지 계속 보낸 다음(`--flush-timeout-ms`, 기본 10초) BYE를 보냅니다. 서버와 각 클라이언트는 다음 줄을 출력합니다.

```
replicated state hash: 7660947a7b0a936e (tick 300, 1200 entities)
```

해시는 복제되는 모든 엔티티의 (서버 슬롯, 세대, 아키타입, 역양자화된 값의 비트)를 서버 슬롯 순으로 묶은 것입니다. 문자열·리스트는 그 바이트의 해시이며, 그 안의 엔티티 참조는 그 클라이언트가 가진 대상만 남깁니다(5.3의 8번). 서버는 자기 월드 값을 양자화·역양자화해서 계산하고, 클라이언트는 **자기 ECS 월드에 실제로 들어 있는 값**을 서버 슬롯으로 되돌려 계산합니다. 두 해시가 같으면 클라이언트 월드가 서버 상태의 양자화 사본과 비트 단위로 같다는 뜻입니다. 서버는 클라이언트마다 대역폭(B/tick, 데이터그램 수, 패리티), 기준선 나이, 관측한 손실과 중복, RPC 수와 버린 재전송 사본 수를 출력하고, 클라이언트는 적용·미완성 스냅샷 수, 관측한 손실, RPC 재전송 수를 출력합니다.

`--wait-clients N`은 클라이언트 N개가 접속할 때까지 첫 틱을 미룹니다.

측정값 (localhost, 클라이언트 3개 중 1개는 중간 참여, 클라이언트당 UDP 페이로드):

| 예제 | 손실 없음 | 손실 20% · 지연 30±10ms (양방향) |
|---|---|---|
| arena (복제 엔티티 약 30개, RPC 있음) | 206 B/tick, 기준선 나이 1.0틱 | 212 B/tick, 기준선 나이 5.1틱, RPC 하나를 ack까지 평균 4번 다시 보냄 |
| boids (1200마리, 조각화) | 4.2~4.4 KB/tick | 7.9~8.1 KB/tick (패리티 13%, 기준선 나이 6틱) |

어느 경우든 모든 클라이언트가 서버와 같은 해시로 수렴했습니다.

### 5.5.5 남은 한계

엔티티 핸들·문자열·리스트·배열·사전 필드는 복제되고, 컬렉션 안의 엔티티 참조도 클라이언트 핸들로 이어집니다(5.3의 5~8번). 큰 리스트는 바뀐 원소만 델타로 갑니다(5.5.3).

**실제 네트워크의 남은 한계**: 렌더링 속도의 보간이 없습니다(클라이언트는 서버 틱마다 한 번 돌고, 잃어버린 틱만 앞뒤 스냅샷 사이로 보간합니다: 5.6절). `Net.View`도 `--budget`도 쓰지 않으면 매 틱 모든 복제 엔티티의 변경을 보냅니다(boids 1200마리는 클라이언트당 약 4KB/틱 = 60Hz에서 250KB/s). 예산을 두면 아직 확인되지 않은 변경이 스냅샷마다 다시 실리므로(기준선이 프레임 단위), 새 변경을 실을 자리는 왕복 시간이 길수록 줄어듭니다(로드맵 8.3). `--key` 없이 실행하면 패킷이 평문이라 경로 위의 관찰자가 세션 토큰을 볼 수 있습니다(위조한 CONNECT로 연결을 끊을 수는 없음). `--key`는 키를 아는 모든 사람을 믿는 사전 공유 키 방식이라, 플레이어마다 접속 권한을 주고 빼는 공개 서버에는 플레이어별 인증이 필요합니다(로드맵 8.3). 스냅샷은 16MB 이하여야 합니다.

## 5.6 클라이언트 → 서버: 자동 RPC

`client` 코드에서 서버 상태를 바꾸는 엔티티 메서드를 호출하면, 그 호출은 **RPC 요청으로 컴파일**됩니다. 프로그래머는 네트워크 코드를 쓰지 않습니다.

```csharp
// examples/arena.sijo
public client void Input()
{
    if (Side == ETeam.Red && Time.Tick % 120 == 0)
    {
        Shield();                        // Shield()는 Hp를 씀 → 자동 RPC
    }
}

public void Shield()
{
    Hp = Math.Min(Hp + 15, Rules.MAX_HP);
}
```

- 판정: 효과 추론에서 "클라이언트 함수가 호출하는 메서드가 (어떤 아키타입에서든) 월드를 변경하는가"를 보고 호출 지점을 `Rpc`로 표시합니다. 클라이언트 코드의 요약에는 RPC 대상의 쓰기가 포함되지 않습니다(그 쓰기는 서버에서 일어나므로 복제 추론에도 영향 없음).
- 형식: 엔티티 간 지연 메시지와 **같은 명령 형식**(대상, 메서드 ID, 인자 바이트)입니다. 네트워크 계층이 클라이언트 핸들을 서버 엔티티 ID(+세대)로 바꿔 보냅니다.
- 신뢰성: 스냅샷과 달리 입력은 잃어버리면 안 되므로 RPC는 **신뢰성 있게** 보냅니다. RPC마다 순번을 붙여 클라이언트 큐에 넣고, 서버가 스냅샷 헤더로 ack할 때까지 매 클라이언트 패킷에 다시 넣습니다(한 패킷에 다 들어가지 않으면 여러 패킷으로 나눔). 서버는 다음에 올 순번만 받아들이므로 중복은 버리고, 각 RPC를 보낸 순서대로 정확히 한 번 실행합니다. 흐름 제어로 클라이언트당 틱마다 256개까지만 받고 나머지는 ack하지 않아 다음 틱에 다시 오게 합니다.
- 서버 권한: 서버는 다음 틱 시작 시 요청을 실행합니다. 메서드 ID가 컴파일러가 RPC로 만든 메서드 목록(생성된 `sijo_rpc_ok`)에 없거나, 인자 크기가 맞지 않거나, 대상 엔티티가 이미 사라졌으면(세대 불일치) 버립니다. `bool` 인자는 0/1로 정규화합니다. 메서드 본문은 서버의 상태와 규칙(범위 계약 포함)으로 실행되므로 클라이언트가 값을 조작할 수 없습니다.
- 타이밍: 한 프로세스 모드(손실 없음)에서는 틱 t의 클라이언트 프레임이 낸 RPC가 틱 t+1 시작에 실행되어 결과가 결정론적입니다. 실제 네트워크에서는 도착 시각에 따라 실행 틱이 달라지므로, 서버 결과가 입력 도착 시각에 따라 달라지는 것은 다른 온라인 게임과 같습니다. 클라이언트 프레임은 서버 틱마다 정확히 한 번, 틱 순서대로 돕니다. 스냅샷을 잃어버린 틱(최대 32틱 연속)은 다음 스냅샷이 도착했을 때 먼저 재구성해 실행합니다: 엔티티는 앞 스냅샷의 것이고, float 필드는 앞뒤 스냅샷 사이를 선형 보간합니다(양자화 단계의 정수 연산, 또는 IEEE float 연산이라 모든 클라이언트가 같은 값을 계산). 나머지 필드는 앞 스냅샷 값을 유지합니다. 그래서 `Time.Tick % 120 == 0`인 입력 같은 틱 기반 클라이언트 코드가 손실로 건너뛰어지지 않습니다(30% 손실 테스트에서 입력 60개 중 59개 도착, 마지막 하나는 실행이 끝날 때 전송 중). 재구성한 틱은 기준선이 되거나 ack되지 않으며, 실제 스냅샷이 오면 그 값이 그대로 적용됩니다.
- 인자: 값 타입과 **문자열**(길이 + UTF-8 바이트; 서버가 길이·UTF-8을 검증하고 틀리면 버림). 반환값, ref/out, 리스트, 엔티티 핸들은 안 됩니다(E0608), 문자열을 담은 struct도 안 됩니다(E0249). 정적 함수로 서버 상태를 바꾸는 호출은 오류(E0601).
- **예측과 재조정**: RPC 메서드가 복제되는 상태만 읽고 자기 엔티티만 바꾸면(생성·파괴·메시지·원격 쓰기·`Random`·`Print` 없음, 모든 아키타입에서) 컴파일러가 *예측 가능*으로 표시합니다. 클라이언트는 그런 RPC를 서버로 보내면서 **자기 월드에서도 바로 실행**하므로, 같은 클라이언트 프레임의 다음 코드가 결과를 봅니다(왕복 지연 없음). 스냅샷 헤더의 RPC 확인 번호는 "그 틱 상태에 이미 반영된 마지막 RPC"입니다(서버는 받은 RPC를 다음 틱 시작에 실행한 뒤 그 틱을 캡처). 그래서 클라이언트는 프레임을 적용할 때마다 예측이 건드린 엔티티를 그 프레임의 값으로 되돌리고, 아직 반영되지 않은 예측 RPC만 순서대로 다시 실행합니다. 서버도 같은 값을 바꾸면(예: 시간에 따른 감소) 클라이언트는 서버 값 위에 미확인 입력을 얹은 상태가 됩니다. 게임이 끝나면 실행되지 않을 RPC의 예측은 버리므로, 마지막 상태는 서버와 같습니다(테스트: 지연 80±20ms·손실 20%에서 클라이언트가 매 프레임 자기 입력을 모두 보고, 끝에서 서버와 같음. 마지막 틱에 보낸 RPC처럼 서버가 작별 인사 직전에 확인만 하고 실행하지 않은 예측도 버려짐). `--no-predict`로 끌 수 있습니다. 복제되지 않는 필드를 읽는 메서드(예: `arena.sijo`의 `Shield`는 서버 전용 `Hp`를 읽음)는 예측하지 않습니다.

## 5.7 분산 시뮬레이션 — 샤드

월드를 공간으로 나눠 샤드에 맡기고, 부하에 따라 경계를 다시 잡고, 경계를 넘은 엔티티의 권한을 넘기되(5.7.5절) 게임 코드는 분산을 의식하지 않습니다. 샤드는 **별도 프로세스**(또는 한 프로세스 안의 별도 월드)이고, 같은 프로그램·시드·입력이면 **샤드 수와 상관없이 한 프로세스 실행과 출력·월드 체크섬·복제 상태 해시가 비트 단위로 같습니다**. 스레드 수, 샤드 사이 네트워크의 손실·지연·중복(`--sim-*`), 샤드 하나가 죽었다가 체크포인트에서 살아나는 것과도 무관합니다(테스트 `tests/shard_e2e.rs`).

```bash
prog --ticks 600 --shards 4                       # 샤드 월드 4개를 한 프로세스에서 (같은 교환을 메모리로)
P=127.0.0.1:7001,127.0.0.1:7002,127.0.0.1:7003     # 샤드마다 HOST:PORT 하나, 샤드 번호 순
prog --shard-of 3 --shard-id 1 --peers $P &        # 샤드 프로세스 1, 2
prog --shard-of 3 --shard-id 2 --peers $P &
prog --shard-of 3 --shard-id 0 --peers $P --ticks 600            # 샤드 0 = 코디네이터 (+ 프로세스 안 클라이언트)
prog --shard-of 3 --shard-id 0 --peers $P --server 7777 --ticks 0  # 또는 UDP 클라이언트의 게이트웨이
```

### 5.7.1 모델: 같은 구조, 주인이 계산

- **구조는 모든 샤드가 같습니다.** 슬롯 표(엔티티 핸들의 인덱스·세대, 빈 슬롯 목록)와 모든 아키타입 테이블의 행 순서가 모든 샤드에서 같습니다. 구조를 바꾸는 생성·파괴가 모든 샤드에서 같은 전역 순서로 적용되기 때문입니다. 데이터는 행마다 **주인 샤드**에서만 언제나 유효하고, 다른 샤드에는 그 샤드가 읽는 컴포넌트의 사본만 유효합니다(5.7.3).
- **주인.** 위치가 있는 아키타입(`[Spatial]` 또는 `Pos`/`Position` 필드, 5.8과 같은 규칙)은 X 좌표의 **슬랩**으로 나눕니다. 경계는 X의 분위수(엔티티 수 기준 균등)이고, 엔티티는 슬랩을 히스테리시스 h만큼 넘어서야 다른 샤드로 넘어갑니다(5.7.5). 위치가 없는 아키타입은 `슬롯 번호 % 샤드 수`가 주인입니다.
- **시스템마다 실행 방식**을 컴파일러가 정하고 `sijoc explain`의 `[shards]`에 이유와 함께 보여 줍니다.
  - *분할*(partitioned): 엔티티 시스템. 샤드마다 자기가 주인인 행만 돕니다(행 루프에 주인 검사 하나, 샤드가 아니면 원래 루프. 메서드는 두 루프에 모두 인라인되므로 샤드가 아닐 때의 속도는 그대로).
  - *복제*(replicated): 모든 샤드가 모든 행을 똑같이 돕니다. `Spawn`이 돌려준 핸들을 나중에 고칠 수 없는 방식으로 쓰는 시스템(한 프로세스에서도 직렬로 도는 경우, 4.8절)과 월드를 바꾸는 `Game.Update`입니다.
  - *코디네이터*: 읽고 출력만 하는 `Game.Update`는 샤드 0에서만 돕니다.
- **명령 적용은 복제됩니다.** 스테이지가 끝나면 샤드들이 분할 시스템의 지연 명령·생성·출력을 주고받고, **모든 샤드가 모든 명령을 같은 순서로** `sijo_apply`합니다. 메시지 본문(원격 메서드, RPC)이 읽는 컴포넌트는 모든 샤드에 사본이 있으므로(5.7.3) 모든 샤드가 한 프로세스와 같은 값을 계산합니다. 메시지가 만든 명령도 같은 큐의 끝에서 모든 샤드가 똑같이 처리하므로 다시 주고받을 필요가 없습니다.

```
샤드 i:  스테이지 시작 이미지 ─▶ 분할 시스템(자기 행) ─▶ 배리어: 명령·생성·출력·사본·이양·부하를 모든 샤드와 교환
                                                     ─▶ 생성을 전역 순서로 합침(슬롯 할당) ─▶ 명령을 전역 순서로 sijo_apply ─▶ 다음 스테이지
```

### 5.7.2 전역 순서 키와 엔티티 핸들

샤드 수와 무관한 순서는 한 프로세스의 적용 순서(4.9절, `codegen.rs`의 `systems`·`sijo_apply`)에서 나옵니다.

- 한 스테이지의 명령은 **시스템 순서**로 쌓입니다. 직렬 시스템은 공용 버퍼에 바로, 병렬 시스템은 스레드별 버퍼에 쌓았다가 아키타입 루프마다 스레드 순서로 합칩니다. 스레드 t는 t-1 다음의 연속된 행 구간을 돌므로 스레드 순서 = **행 순서**이고, 한 엔티티 안에서는 **프로그램 순서**입니다(태스크 그룹은 구성원 순서로 합침).
- 메시지가 만든 명령은 큐 끝에 붙어 FIFO로 처리됩니다(라운드 순서).
- 생성은 직렬 시스템에서는 호출 즉시(행 순서) 슬롯을 받고, 병렬 시스템에서는 아키타입 루프가 끝날 때 **생성된 아키타입마다** 스레드 순서로 받습니다(`sijo_tmerge_all`). 슬롯은 빈 목록(LIFO)에서 나오므로 생성·파괴의 순서가 핸들을 정합니다.

그래서 **샤드 수와 무관한 키**는 다음과 같습니다. 행 순서는 모든 샤드에서 같으므로 행 번호를 그대로 키로 씁니다.

| 대상 | 키 | 비고 |
|---|---|---|
| 지연 명령 | (시스템 번호, 시스템 안 아키타입 위치, 보낸 엔티티의 행, 그 엔티티 안의 순번) | 시스템 경계는 명령 버퍼 표시로, 행은 보낸 엔티티 핸들로 찾음 |
| 생성 | (시스템, 아키타입 위치, 병렬 시스템이면 생성된 아키타입, 생성한 엔티티의 행, 그 행의 n번째 생성) | 위의 두 할당 방식을 그대로 재현 |
| `Print` | (시스템, 아키타입 위치, 행, 순번) | 코디네이터가 모아 한 프로세스 순서로 출력 |

- 분할 시스템의 `Spawn`은 샤드에서 언제나 **임시 핸들**(아키타입·스레드·행, 4.8절)을 돌려줍니다. 배리어에서 모든 샤드가 모든 생성 레코드(키 + 모든 컴포넌트의 정확한 이미지)를 키 순으로 합쳐 같은 슬롯을 할당하고, (보낸 샤드, 임시 핸들) → 진짜 핸들 표로 `this`의 핸들 필드, 명령 대상, 받은 사본 안의 핸들을 고칩니다. 한 스테이지에서 분할 시스템이 생성한 뒤 **복제** 시스템이 생성하면, 복제 시스템은 바로 슬롯을 받아야 하므로 그 앞에 생성만 합치는 배리어를 하나 더 둡니다(`explain`의 "plus spawn merges").
- **엔티티 핸들은 샤드 수와 무관하게 같습니다.** 슬롯 할당과 해제가 모든 샤드에서 한 프로세스와 같은 순서로 일어나기 때문입니다. 핸들(인덱스·세대)은 월드 체크섬, 복제 상태 해시(서버 슬롯·세대), 난수 키(`(시드, 틱, 엔티티, 호출 지점)`), 상태 파일에 모두 들어가며, 이 셋 다 테스트가 한 프로세스와 비교합니다.

### 5.7.3 사본: 모든 샤드, 코디네이터, 헤일로

컴포넌트마다 "누가 다른 샤드의 행을 읽는가"로 사본을 보낼 곳을 정합니다. 사본은 그 컴포넌트를 **분할 시스템이 바꾼** 스테이지의 배리어에서, 스테이지 시작 이미지와 다를 때만 갑니다(복제 실행이 바꾼 값은 모든 샤드가 이미 똑같이 계산했으므로 보내지 않음).

| 읽는 코드 | 사본 | 예 |
|---|---|---|
| 메시지 본문·RPC(모든 샤드가 적용), 복제 시스템 | 모든 샤드 | arena `Ship.Hp`(`Shield`가 읽음) |
| 분할 시스템이 핸들로 읽거나 반경이 증명되지 않은 쿼리로 훑음 | 모든 샤드 | arena `Ship.Pos`(`steer`가 모든 배를 훑음) |
| 코디네이터에서 도는 `Game.Update`, 클라이언트 복제 | 코디네이터 | boids `Neighbours` |
| 분할 시스템의 근접 루프만(반경 R이 `spatial`로 증명됨) | **헤일로**: 슬랩 ± (h + 1.01R)에 드는 샤드 | boids `Pos`, `Vel`: R = 12, h = 3 |
| 아무도 다른 행에서 읽지 않음 | 보내지 않음(권한 이양 때만) | arena `Ship.Cooldown` |

헤일로가 정확하려면 질의하는 엔티티가 루프에서 쓰는 위치가 스테이지 시작 위치여야 하고(주인 샤드의 슬랩 ± h 안), 그 근처 R 안의 엔티티가 모두 사본으로 있어야 합니다. 컴파일러는 다음을 모두 확인한 루프만 헤일로로 보내고, 아니면 모든 샤드로 보내며 `explain`에 이유를 씁니다(예: arena의 `Bullet.Update`는 "may move this entity before the loop runs").

- 반경이 상수이고, 거리 조건이 X 축(슬랩을 자르는 축)을 포함하며, 위치 필드가 두 아키타입의 분할 위치 필드다.
- 시스템이 루프보다 **앞에서** `this`의 위치를 쓰지 않는다(시스템 본문과 루프가 든 헬퍼를 문장 순서로 확인).
- 지연 명령이나 메시지가 그 위치를 바꾸지 않는다(바꾸면 적용 중에 헤일로 소속이 달라짐).

샤드에서 헤일로 루프는 사본이 유효하지 않은 행을 건너뜁니다(격자를 만들 때와 전체 순회에서 한 번의 바이트 검사). 그런 행은 증명에 따라 거리 조건을 통과할 수 없으므로 결과는 그대로입니다. 반경이 엔티티마다 다른 루프(`dyn_r2`)와 증명되지 않은 전역 `Query`는 **전체 미러링**(모든 샤드)으로, 고칠 수 없는 핸들 사용은 **복제 실행**으로 대신합니다. 둘 다 정확하고 느릴 뿐입니다.

**코덱.** 클라이언트 복제의 프레임·델타 구조를 그대로 따릅니다: 프레임 = 스테이지 시작에 찍은 주인 행의 컴포넌트 이미지, 델타 = 슬롯 번호 오름차순 레코드(슬롯 차이 varint, 세대, 들어옴/나감 표시, 컴포넌트 마스크, 바뀐 컴포넌트). 다른 점은 값이 **양자화되지 않은 정확한 비트 이미지**라는 것입니다(엔디언과 무관한 리틀 엔디언; 문자열은 길이 + UTF-8, 리스트·배열·사전은 원소 수 + 원소, 핸들은 인덱스·세대). 헤일로에 들어온 엔티티는 헤일로 컴포넌트 전체를, 머문 엔티티는 바뀐 것만, 나간 엔티티는 "나감" 레코드를 보냅니다. 주인은 엔티티마다 "사본을 가진 샤드" 비트 집합을 두고, 받는 쪽은 슬롯마다 "헤일로 사본 유효" 표시를 둡니다.

### 5.7.4 배리어와 메시지

틱마다 배리어는 스테이지 수만큼(+ RPC가 있는 프로그램은 틱 시작에 하나, + 생성 합치기)입니다. arena는 4개(RPC 1 + 스테이지 3), boids는 2개입니다. 배리어마다 각 샤드는 다른 모든 샤드에 메시지 하나를 보내고 모두에게서 하나씩 받습니다(록스텝).

```
머리: 버전(SIJO_SH_VERSION = 1) u8 · 종류 u8 · 배리어 번호 u64 · 틱 u32 · 보낸 샤드 u16 · 멈춤 u8
구획 6개, 각각 [바이트 수 u32][내용]:
  0 명령    분할 시스템의 지연 명령: 키 + 한 프로세스와 같은 SijoCmd 형식(종류·대상·필드·오프셋·크기·값·인자 바이트)
            (RPC 배리어: 코디네이터가 받은 RPC 명령)
  1 생성    키 · 아키타입 · 임시 핸들 · 모든 컴포넌트의 이미지
  2 부하    주인인 위치 엔티티 수 [+ 재조정 표본]
  3 출력    키 · 텍스트 (코디네이터에게만)
  4 사본    5.7.3의 델타 레코드
  5 이양    슬롯 · 세대 · 새 주인 · 헤일로 비트 집합 [+ 새 주인에게: 모든 컴포넌트]
```

명령 레코드는 한 프로세스의 명령 버퍼 형식(`SijoCmd`, 메시지 인자 바이트 포함)을 그대로 실어 나르므로, 이 계층은 명령의 내용을 해석하지 않고 바이트를 옮기기만 합니다. 형식이 맞지 않는 프로그램끼리는 처음 만날 때 **샤드 프로토콜 해시**(아키타입·컴포넌트·필드 타입·사본 경로·시스템 실행 방식·배리어 구성)로 거절합니다.

### 5.7.5 권한 이양과 재조정

- **이양.** 스테이지 끝 배리어마다 주인은 위치 엔티티의 X가 자기 슬랩을 h 넘게 벗어났는지 봅니다(h = 헤일로 반경의 1/4, 헤일로가 없으면 0). 넘으면 모든 샤드에 새 주인을 알리고, 새 주인에게 모든 컴포넌트와 "사본을 가진 샤드" 집합을 보냅니다. 모든 샤드가 같은 배리어에서 같은 정보를 받으므로 주인 표는 언제나 일치합니다. 새로 생긴 엔티티는 모든 샤드가 전체 상태를 가지므로 모든 샤드가 같은 규칙(슬랩, 위치 없으면 슬롯 % N)으로 주인을 정합니다.
- **재조정.** 틱의 마지막 배리어에서 모든 샤드가 같은 부하(주인인 위치 엔티티 수)로 불균형(최대/평균)을 계산합니다. 1.25를 넘고 마지막 재조정에서 30틱 이상 지났으면, 다음 배리어에 샤드마다 X 표본(정렬된 최대 256개와 개수)을 싣고, 모든 샤드가 같은 가중 분위수로 새 경계를 계산해 그다음 배리어부터 씁니다.
- 경계와 이양 시점은 시뮬레이션 결과에 영향을 주지 않습니다(결과는 주인과 무관). 정해진 입력으로 모든 샤드가 같은 결정을 내리므로 복구한 샤드도 같은 이양을 다시 합니다.

### 5.7.6 샤드 사이 전송

샤드 쌍마다 **신뢰성 있는 채널**을 sijo_net.h의 데이터그램 계층 위에 둡니다. 그래서 `--key`(XChaCha20-Poly1305)와 `--sim-loss/--sim-latency-ms/--sim-jitter-ms/--sim-dup`이 그대로 적용됩니다. RPC 채널의 방식(순번, ack될 때까지 재전송, 순서대로만 받음)을 큰 메시지용으로 넓힌 것입니다: 메시지를 번호 붙은 조각(≤ 1171바이트)으로 나누고, 받는 쪽은 누적 ack + 그 뒤 64조각 비트맵을 보내며, 보내는 쪽은 비트맵에서 빠진 조각을 바로, 끝 조각은 타이머(관측한 최소 왕복 시간의 1.5배 + 1ms, 조각마다 지수 백오프)로 다시 보냅니다. 받는 쪽은 메시지를 통째로, 순서대로 넘깁니다. 배리어에서 기다리는 샤드는 보낸 직후와 데이터그램이 도착한 뒤 0.3ms 동안은 잠들지 않고 폴링합니다(조각마다 깨어나는 비용이 조각보다 비쌈, 5.7.9).

- 프로세스마다 시작할 때 무작위 **에포크**를 정하고 HELLO(프로토콜 해시, 샤드 수, 복구 지점)로 서로 확인한 뒤 시작합니다. 새 에포크의 HELLO는 그 상대가 다시 시작했다는 뜻이라 양방향 스트림을 처음부터 다시 엽니다.
- 같은 기계의 샤드 프로세스는 코어를 나눠 쓰므로, OpenMP 대기 정책을 정하지 않았으면 `OMP_WAIT_POLICY=passive`로 자기 자신을 다시 시작합니다(기본 정책의 바쁜 대기는 다른 샤드의 코어를 빼앗아 boids 2샤드의 틱이 7ms → 0.7ms로 차이남).

### 5.7.7 장애 복구

`--checkpoint-dir DIR --checkpoint-every K`(기본 60)이면 샤드마다 K틱마다 틱 끝에 **체크포인트**를 씁니다: 월드는 `--save-state` 형식(`shardI-TICK.state`), 샤드 상태(배리어 번호, 경계, 슬롯별 주인·헤일로 표시·사본 집합, 재조정 상태)는 `shardI-TICK.meta`(마지막에 이름을 바꿔 쓰므로 있으면 완전함). 최근 두 개를 남기고, 각 샤드는 그 이후 다른 샤드에 보낸 메시지를 **메시지 로그**로 메모리에 둡니다. 코디네이터가 받은 클라이언트 입력(RPC)도 RPC 배리어 메시지로 나가므로 같은 로그에 들어갑니다.

샤드 하나가 죽으면 다른 샤드들은 다음 배리어에서 기다립니다(`--shard-timeout-ms`마다 경고). 같은 주소로 `--recover`를 주어 다시 시작하면:

1. 가장 새 완전한 체크포인트를 읽습니다(월드 + 샤드 상태).
2. HELLO에 "이 배리어 이후를 달라"를 실어 보내고, 다른 샤드들은 로그에서 그 뒤 메시지를 차례로 다시 보냅니다.
3. 결정론적으로 다시 시뮬레이션합니다. 자기가 다시 보내는 메시지는 받는 쪽이 배리어 번호로 이미 받은 것을 버리므로, 출력도 두 번 찍히지 않습니다. 따라잡으면 그대로 록스텝에 합류합니다.

테스트는 `--die-at-tick`(갑작스러운 종료)과 실시간 실행 중 SIGKILL 모두에서, 손실·중복이 있는 링크로, 끝의 월드 체크섬·출력이 한 프로세스와 같음을 확인합니다. 코디네이터(샤드 0)는 복구하지 않습니다(클라이언트 연결과 프로세스 안 클라이언트의 상태가 함께 사라지므로 다시 시작해야 함, 로드맵 8.3).

### 5.7.8 클라이언트: 코디네이터가 게이트웨이

클라이언트는 샤드마다 붙지 않고 **샤드 0에만** 붙습니다. 복제되는 컴포넌트는 사본 경로에 "코디네이터"가 있으므로 코디네이터의 월드에서 언제나 유효하고, 그래서 한 프로세스 서버와 같은 코드(프레임, 확인된 기준선 델타, 조각화·패리티, `Net.View`, `--budget`, 늦은 참여의 전체 상태, 예측·재조정, 종료 수렴 확인)가 그대로 돕니다. 클라이언트의 RPC는 코디네이터가 받아 틱 시작 배리어에서 모든 샤드에 보내고, 모든 샤드가 같은 틱에 실행합니다. 이 방식을 고른 이유: 클라이언트가 샤드 경계를 몰라도 되고, 이양 때 연결을 옮길 일이 없으며, 기준선·예산·시야가 한곳에 있습니다. 대신 코디네이터는 복제 컴포넌트의 변경을 모든 샤드에서 받습니다(5.7.9의 측정).

실행이 끝나면 다른 샤드들이 자기 행 전체를 코디네이터에 보내고(모음), 코디네이터가 월드 체크섬·`--save-state`·요약을 씁니다.

- 시간이 드는 곳(16000마리, 샤드 프로세스 4개, `--timing`, 틱·샤드당): 시스템 1.8~1.9ms(6.1ms의 4분의 1 + 모든 행의 주인 검사), 메시지 만들기(스테이지 시작 이미지·비교·패킹) halo 0.22~0.23ms / hash 0.42~0.48ms, 배리어 대기 halo 0.11~0.18ms / hash 0.31~0.45ms, 받은 것 설치 0.01ms(hash의 코디네이터 0.15ms), 명령 적용 0.02~0.04ms.
- 배리어 하나의 바닥 비용은 localhost에서 약 50µs입니다. 메시지가 도착하는 동안에는 잠들지 않고 폴링하므로 boids 4000마리 2샤드의 배리어 대기는 틱마다 0.11ms입니다(조각마다 잠들면 VM이 깨어나는 비용 때문에 0.92ms).

### 5.7.10 한계

- 샤드는 모든 슬롯·행의 구조를 가지므로 메모리는 샤드 수로 줄지 않습니다(계산과 사본 전송만 나뉨). 행마다 테이블에 자리가 있지만 주인이 아닌 행의 값은 사본이 오기 전까지 오래된 값입니다.
- 복제 실행(고칠 수 없는 핸들 사용, 월드를 바꾸는 `Game.Update`)과 전체 미러링은 정확하지만 나누어지지 않습니다. 명령 적용은 언제나 모든 샤드가 합니다(명령이 많고 메시지 본문이 무거우면 그만큼 반복).
- 록스텝이라 틱마다 배리어 수 × 샤드 간 지연이 듭니다(같은 데이터센터 전제). 코디네이터는 복구하지 않고(5.7.7), 클라이언트 연결이 코디네이터 하나에 모입니다.
- 비순수 `extern` 호출은 분할 시스템에서는 주인 샤드에서 엔티티마다 한 번, 복제 시스템에서는 샤드마다 한 번 실행됩니다.

### 5.7.11 영속성 `[Persistent]`

체크포인트는 샤드 장애를 위한 것이고 같은 실행 안에서만 쓰입니다. 실행을 넘어 남는 상태(플레이어 인벤토리 등)는 Verse의 persistable처럼 필드에 표시하고, 실행 파일에 `--store DIR`을 주면 켜집니다.

```csharp
public class Player : Entity
{
    [PersistentKey] public string Account;          // 저장소에서 이 엔티티의 이름
    [Persistent] public mut int Gold = 10;          // 키 아래에 남음
    [Persistent] public mut List<string> Items;
    [Persistent] public mut int in 0..100 Level = 1;
    public mut int Seen;                            // 표시 없음: 실행마다 처음부터
}
// Spawn(new Player { Account = "ann" });          // 저장소에 "ann"이 있으면 그 값으로 시작
```

- **규칙**(`E0269`): `[PersistentKey]`는 엔티티 클래스 사슬에 하나, `string` 필드이고 그 자체는 `[Persistent]`가 아님. `[Persistent]` 필드가 있는 클래스(하위 클래스 포함)는 키가 있어야 함. 엔티티 참조·델리게이트는 다른 실행에서 뜻이 없으므로 담을 수 없음(리스트·배열·사전·구조체 안에 있어도). 컴포넌트의 필드는 영속이 아님(엔티티 클래스의 필드로 둠). 하위 클래스는 부모의 키와 영속 필드를 물려받고 자기 영속 필드를 더할 수 있음.
- **불러오기**: 엔티티가 생긴 명령 적용(`sijo_apply`)의 끝에서, 키에 해당하는 레코드가 있으면 그 값이 초기값과 `new T { ... }`의 값을 덮어씁니다. 그래서 첫 `Update`부터 저장된 값을 보고, 생성이 결정론적 순서(전역 명령 순서)로 적용되므로 스레드·샤드 수와 무관합니다. 범위 타입은 불러올 때도 포화합니다. 엔티티마다 숨은 플래그(`__persisted`)가 한 번만 불러오게 합니다.
- **저장**: 틱 끝과 `Destroy` 직전에 엔티티의 영속 값을 메모리 안 저장소(키 → 레코드, 해시 색인)에 옮기고, `--store-every N`틱(기본 60)마다와 실행이 끝날 때 바뀐 클래스의 파일을 씁니다. 같은 실행 안에서 파괴 후 같은 키로 다시 생성하면 마지막 값을 이어받습니다. 파일은 `DIR/<클래스>.store`이고 임시 파일에 쓴 뒤 이름을 바꾸므로 중간에 죽어도 이전 파일이 남습니다. 레코드는 그 실행에 나오지 않은 키도 그대로 유지합니다.
- **형식과 이주**: 상태 파일(10.3절)과 같은 텍스트 형식과 규칙입니다. 헤더에 필드 이름과 타입 서명이 있고, 다음 버전의 프로그램은 이름과 서명이 같은 필드만 읽습니다. 타입이 바뀌었거나 새로 생긴 필드는 초기값을 유지하고(`~`는 레코드에 그 값이 없음을 뜻함), 없어진 필드는 건너뜁니다.

  ```text
  SIJO-STORE 1
  class Player
  fields 3
  field Gold int
  field Items list<string>
  field Level int
  records 2
  rec s616e6e | 22 | [3 s6c6f6f7433 s6c6f6f7436 s6c6f6f7433 ] | 1
  rec s626f62 | 60 | [2 s6c6f6f7433 s6c6f6f7433 ] | 1
  end
  ```
- **샤드와 클라이언트**: 영속 필드는 모든 샤드로 복제 경로가 잡혀 코디네이터(샤드 0)가 모든 행의 최신 값을 가지며, 파일은 코디네이터만 씁니다(`--shards N`과 샤드 프로세스 모두). 모든 샤드가 같은 레코드를 같은 순서로 불러오므로 체크섬이 같습니다. 클라이언트 월드는 저장소를 읽지도 쓰지도 않고 서버가 보낸 값을 받습니다.
- **검증**(`tests/e2e.rs`의 `persistent_fields_outlive_the_run`, `tests/programs/persist.sijo`): 8틱 실행이 쓴 저장소에서 다시 시작하면 스레드 1/4와 `--shards 3`이 같은 출력·체크섬·저장소 파일을 만들고, 틱 5에 파괴되어 틱 7에 다시 생성된 엔티티가 마지막 값을 이어받으며, `Level`의 타입을 `float`로 바꾼 다음 버전은 `Gold`·`Items`만 불러오고 `Level`은 초기값(2.5)으로 시작합니다. 생성 C는 gcc·clang `-Wall -Wextra -pedantic -Werror`에서 경고가 없고 ASan/UBSan에서 깨끗합니다. 규칙은 `tests/diagnostics.rs`의 `persistence_rules`.
- **한계**: 저장소는 로컬 디렉터리의 파일입니다(데이터베이스·여러 서버가 공유하는 저장소는 아님). 쓰기는 클래스 단위로 파일 전체를 다시 씁니다(바뀐 레코드만이 아님). 키가 실행 중에 바뀌면 그 뒤 값은 새 키 아래에 저장됩니다(불러오기는 생성 때 한 번). 샤드 프로세스는 각자 저장소를 읽으므로 모두 같은 파일(공유 디렉터리나 복사본)을 `--store`로 받아야 합니다.

### 5.7.12 언어 기능과 맞물리는 곳

샤드 런타임은 "아키타입 테이블 + 핸들 + 명령 버퍼"만 봅니다. 테이블은 `sijo_sh_count/ent/x/pack/unpack(아키타입, 행, 컴포넌트 위치)` 디스패처(생성 코드, `src/shard.rs`)로만 다루고, 명령은 `SijoCmd` 필드와 인자 바이트를 그대로 옮깁니다. 아래 언어 기능은 모두 이 추상 안에서 동작하며 `tests/shard_e2e.rs`가 샤드 수와의 무관성을 확인합니다.

- **동적 컴포넌트**(4.4.1절): 조합(`Runner+Stung`)은 클래스의 하위 아키타입이므로 디스패처·코덱·주인·헤일로가 그대로 적용됩니다. `Add`/`Remove`는 지연 명령(`SIJO_CMD_CADD`는 컴포넌트 값을 인자 바이트로 싣고, `SIJO_CMD_CREM`)이라 키와 함께 교환되고, 모든 샤드가 `sijo_apply`에서 같은 순서로 행을 옮기므로 행 순서가 계속 같습니다. 컴포넌트의 `Update`는 분할 시스템입니다(`programs/shards.sijo`의 `Stung`, `programs/components.sijo`).
- **원격 메시지의 리스트·배열 인자**: 원소까지 명령 데이터에 바이트로 들어가므로 그대로 교환됩니다. 명령 데이터는 그 기계의 바이트 순서이므로 샤드 프로세스들은 같은 엔디언이어야 합니다(지금 지원하는 64비트 리틀 엔디언 플랫폼끼리는 문제 없음).
- **다차원 배열**: 사본 코덱이 길이(d0..d2)와 원소를 보냅니다. **엔티티 참조·사전을 담은 컬렉션**: 원소 안의 핸들까지 정확히 보내고 임시 핸들도 고칩니다. 클라이언트 쪽의 원소 단위 델타는 코디네이터에서 그대로 돕니다.
- **제네릭 엔티티 클래스, 인터페이스 기본 구현, `atomic` 확장**: 인스턴스마다 아키타입, 메서드, 시스템 안의 일이라 샤드 계층과 무관합니다.
- 새 필드 타입을 더할 때는 `src/shard.rs`의 `sh_pack`/`sh_unpack`에 경우를 더합니다. 없으면 샤드 실행에서 그 컴포넌트를 보낼 때 패닉으로 알립니다(한 프로세스 실행에는 영향 없음). `SijoCmd`에 필드가 늘면 `sijo_sh_put_cmd`/`sijo_sh_rd_cmd`에 더하고 `SIJO_SH_VERSION`을 올립니다.

## 5.8 관심 영역과 대역폭 예산

클라이언트 코드가 `Net.View(x, y, radius)`로 자기가 보는 원을 정하면, 서버는 그 클라이언트에게 **원 안의 엔티티와 위치가 없는 엔티티만** 보냅니다. `Net.ClearView()`는 다시 모두 받게 합니다.

```csharp
public class Camera : Entity
{
    public SVec2 Focus;                        // 위치 필드가 아님(Pos/Position/[Spatial] 아님) → 항상 전송
    public client void Look() { Net.View(Focus.X, Focus.Y, 30); }
}
```

- 위치는 `[Spatial]` 필드, 없으면 `Pos`/`Position` 이름의 struct 필드의 `X`(·`Y`)입니다(샤딩과 같은 규칙). 위치가 없는 아키타입은 언제나 보냅니다. 시점을 정하는 엔티티(카메라, 플레이어)는 위치 필드가 아닌 이름으로 두어야 시야를 벗어나도 계속 받습니다.
- 반경 안에 들어오면 보내고, 반경의 1.1배를 벗어나면 뺍니다(경계에서 깜빡이지 않게). 빠진 엔티티는 그 클라이언트에서 파괴되고, 다시 들어오면 그 틱의 전체 값으로 생성됩니다.
- 서버는 클라이언트마다 보낸 틱별로 "그 틱에 보낸 슬롯 집합"(64틱 기록, 비트 집합)을 두고, 델타를 **그 클라이언트가 확인한 틱에 실제로 받은 집합**에 대해 만듭니다. 그래서 기준선 규칙(5.5.2)이 그대로 성립합니다. 한 틱을 시야로 거를지와 그 집합은 그 틱을 처음 보낼 때 정해지고, 같은 틱을 다시 보낼 때(클라이언트를 기다리는 동안의 시작 상태, 종료 시 마지막 프레임)는 그 사이에 시야가 생기거나 없어져도 그대로 씁니다. 그러지 않으면 시작 상태를 전체로 받은 클라이언트를 시야만 가진 것으로 여겨, 시야 밖 엔티티가 그 클라이언트에서 지워지지 않습니다. 이런 인코딩은 그 클라이언트 것이라 다른 클라이언트와 공유하지 않습니다.
- 시야 밖 엔티티를 가리키는 참조는 클라이언트에서 null로 읽히고, 대상이 시야에 들어오면 다시 이어집니다(클라이언트는 프레임마다 프레임에 담긴 서버 슬롯으로 참조를 다시 맞춤). 리스트·배열·사전 안의 참조도 같습니다: 원소는 null로 읽히고, 참조가 키인 사전에서는 그 쌍이 빠졌다가 대상이 보이면 돌아옵니다(5.3의 8번, 테스트 `tests/programs/refview.sijo`).
- 수렴 확인: 서버는 시야가 있는 클라이언트마다 `replicated state hash for client N (its view)`를 그 클라이언트의 마지막 집합으로 계산해 출력하고, 클라이언트의 `replicated state hash`가 그것과 같아야 합니다(테스트로 확인, 손실·지연·중간 참여 포함). 예: 82개 엔티티 중 25개 정도를 보는 테스트 프로그램에서 대역폭이 779 → 192 B/tick.

### 5.8.1 대역폭 예산 (`--budget BYTES`)

서버를 `--budget 1500`처럼 실행하면 게임이 도는 동안 스냅샷 하나의 본문이 클라이언트마다 약 그 바이트 수를 넘지 않습니다. 자리가 없는 변경은 기다리고, **기다린 틱 수 × 가까움 가중치**가 큰 것부터 갑니다.

- 서버는 클라이언트마다 "그 틱의 스냅샷을 적용하면 클라이언트가 갖게 되는 프레임"을 64틱 기록으로 둡니다. 다음 프레임은 **가장 최근에 정한 프레임에서 출발**하므로 클라이언트가 과거로 돌아가지 않습니다: 사라진 엔티티(파괴, 시야 밖)는 바로 빠지고, 바뀐 엔티티마다 새 값을 보내거나 클라이언트가 마지막으로 받은 값으로 둡니다. 스냅샷은 그 클라이언트가 확인한 틱의 프레임에 대한 델타이므로 기준선 규칙(5.5.2)이 그대로 성립합니다.
- 비용: 아직 확인되지 않은 변경은 확인될 때까지 스냅샷마다 다시 실리므로 먼저 셉니다. 남은 자리에 새 변경을 우선순위 순으로 넣고, 처음으로 들어가지 않는 것에서 멈춥니다(뒤의 작은 변경으로 건너뛰지 않음: 방금 보낸 엔티티가 계속 자리를 차지하지 않도록). 아무것도 기다리지 않는데 첫 변경 하나가 예산보다 크면 그것만은 보냅니다.
- 우선순위: 변경이 기다린 틱 수 + 1에 가중치를 곱합니다. `Net.View`가 있는 클라이언트에서는 시야 중심에 가까울수록 최대 4배, 위치가 없는 엔티티(점수판, 카메라)는 4배, 시야 밖 경계 근처는 1배입니다. 시야가 없으면 모두 1배(오래 기다린 순서, 같으면 슬롯 순서).
- 마지막 틱과 종료 시 재전송은 예산 없이 보내 클라이언트가 서버 상태와 같게 끝납니다(`--ticks`가 정해져 있으면 그 틱, 중지 신호를 받으면 그 틱이 마지막). 게임 시작 전(클라이언트를 기다리는 동안)의 시작 상태도 전체로 보냅니다. 중간 참여자의 전체 상태는 예산 안에서 나눠 갑니다.
- 인코딩은 클라이언트마다 따로입니다. 기다리는 동안 이전 값을 가진 문자열·리스트가 표에서 지워지지 않도록, 문자열 표 GC는 클라이언트별 프레임도 표시합니다. 문자열·리스트 변경의 비용은 실제로 갈 크기(확인된 값에 대한 델타가 더 작으면 델타)로 셉니다.
- 통계: `bandwidth budget: … (largest delta while the game ran: N B); M entity changes waited for room (longest wait W ticks)`, UDP 서버는 클라이언트마다 `budget …: largest delta …` 줄을 출력합니다.
- 예: boids 1200마리 300틱(프로세스 안), 예산 없음 4152 B/tick → `--budget 1500`은 1543 B/tick(가장 큰 델타 1503 B, 가장 오래 기다린 변경 6틱), `--budget 400`은 457 B/tick(25틱). 끝의 복제 확인은 모두 OK. 테스트는 손실 링크·시야·UDP 중간 참여까지 확인합니다.

## 5.9 동적 컴포넌트의 복제

런타임에 붙였다 떼는 컴포넌트(1.16절, 4.4.1절)도 같은 경로로 복제됩니다. 따로 붙는 프로토콜은 없습니다.

- **컴포넌트 집합 = 아키타입 번호.** 엔티티의 아키타입은 (클래스, 붙은 컴포넌트 집합)이고, 프레임은 엔티티마다 이미 아키타입 번호를 담습니다(5.5.3). 그래서 컴포넌트 비트 집합은 바뀔 때만 따로 보내는 값이 아니라 아키타입 번호 그 자체입니다. 조합이 바뀐 엔티티는 같은 슬롯·세대의 다른 아키타입이 되고, 스냅샷은 그것을 **생성 레코드**(새 아키타입과 그 엔티티의 모든 복제 값)로 보냅니다. 클라이언트는 옛 테이블의 행을 지우고 새 테이블에 만듭니다. 복제되는 엔티티 참조는 프레임마다 서버 슬롯으로 다시 맞추므로(5.3절의 5) 그 엔티티를 가리키던 참조도 그대로 이어집니다. 조합이 자주 바뀌는 엔티티는 바뀔 때마다 복제 값 전체를 한 번 보내는 비용이 있습니다(필드가 적은 엔티티에서는 컴포넌트 마스크를 따로 보내는 것과 큰 차이가 없음).
- **어느 조합 테이블이 복제되는가**: 클래스가 클라이언트에 보이면(클라이언트 시스템이 돌거나, 클라이언트 코드가 읽는 필드가 있으면) 그 클래스의 모든 조합 테이블이 보입니다(조합은 그 클래스의 하위 아키타입이므로). 컴포넌트의 `client` 메서드나 클라이언트 코드가 읽는 컴포넌트 필드는 그 컴포넌트가 있는 조합들을 보이게 합니다.
- **컴포넌트 필드**는 일반 필드와 같습니다: 클라이언트 코드가 읽는 필드만 복제되고(5.2절), 범위 타입·`[Precision]`으로 비트 수가 정해지며(5.3절), 원격 쓰기·자기 쓰기·`Add`가 더티 플래그를 세웁니다(5.4절). `Add`가 이미 있는 컴포넌트의 값을 바꾸면 그 컴포넌트의 더티 플래그만 섭니다(아키타입이 그대로이므로 델타).
- **클라이언트 코드**는 `Has<C>()`, `Get<C>() is C c`, 컴포넌트 필드, `Query<T, C>()`를 서버와 같은 뜻으로 읽습니다. 클라이언트 월드의 슬롯도 아키타입을 가리키므로 `Has`는 같은 마스크 검사입니다. 클라이언트가 컴포넌트를 바꾸고 싶으면 그 일을 하는 엔티티 메서드를 부르고, 그 호출이 자동 RPC가 되어 서버에서 실행됩니다(5.6절, 예: `public void Ignite() { Add(new Burning { }); }`).
- **확인**: 프로토콜 해시(5.5.3)는 아키타입 목록을 포함하므로 조합이 다른 프로그램끼리는 연결하지 않습니다. 복제 상태 해시와 `replication check`는 아키타입 번호까지 비교합니다. 테스트(`tests/components.rs`)는 컴포넌트를 무작위로 붙였다 떼는 3500개 엔티티를 30% 손실·10% 중복 링크로 복제해 확인이 OK인지, 클라이언트 입력(RPC)으로 붙이는 프로그램이 수렴하는지 봅니다.
