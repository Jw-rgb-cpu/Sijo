# 11. 검증 보고서 — 정확성, 플랫폼 간 동일성, 다른 언어와의 비교

이 장은 Sijo가 실제 게임에 쓸 수 있는 수준인지 확인한 방법과 결과를 정리합니다. 검증은 네 갈래로 했습니다.

1. **코드 검토**: 컴파일러와 런타임의 정의되지 않은 동작, 평가 순서, 정수·부동소수점 의미, 메모리 관리
2. **플랫폼 행렬**: 같은 프로그램을 여러 컴파일러·최적화 옵션·CPU·OS에서 빌드해 출력을 바이트 단위로 비교
3. **문서만 아는 에이전트**: Sijo 문서·예제·컴파일러만 받은 에이전트 4개가 같은 로직을 Sijo와 다른 언어로 작성해 출력을 비교
4. **퍼징**: 테스트 프로그램을 무작위로 변형해 컴파일러 패닉·멈춤, 생성 C 컴파일 실패, 실행 중 메모리 오류, 스레드 수에 따른 결과 차이를 찾음

## 11.1 요약

| 항목 | 결과 |
|---|---|

| 샤드 수와의 무관성 | 예제 3종과 테스트 프로그램을 한 프로세스, 샤드 월드 2~4개, 샤드 프로세스 2~4개(스레드 1/2/4)로 실행: 출력·월드 체크섬·복제 상태 해시가 모두 같음. 손실 20%·지연·지터·중복이 있는 암호화된 샤드 링크, 실행 중 SIGKILL 뒤 체크포인트 복구에서도 같음(5.7절) |

| 다른 언어와의 동일성 | 에이전트들이 C++·C#·Rust·Go·Java·JavaScript·Python으로 같은 로직을 작성: 모든 출력이 바이트 단위로 같음 |
| 임베딩 | C·C++·C#·Python·Rust·Go 호스트에서 같은 그리기 목록과 체크섬. 한 언어에서 저장한 상태를 다른 언어 호스트가 이어서 실행해도 같음 |
| 퍼징 | 변형 프로그램 약 45만 개(그중 약 1만 4천 개는 C까지 생성해 컴파일): 컴파일러 패닉·멈춤 0건. 컴파일러가 받아들인 변형 프로그램 약 1천 개를 ASan·UBSan으로 빌드해 1·3스레드로 실행하고 결과를 비교: 메모리 오류·정의되지 않은 동작·스레드 수에 따른 차이 0건 |

## 11.2 플랫폼 행렬

프로그램 12개(예제 3종, 기능별 테스트 프로그램, 벤치마크)를 아래 조합으로 빌드해 모든 `Print` 줄, 월드 체크섬, 복제 상태 해시를 비교했습니다. 매 커밋 확인은 `tests/cross.rs`가 합니다(도구가 설치된 경우).

| 조합 | 결과 | 같게 만드는 방법 |
|---|---|---|
| gcc `-O2`, 1·4스레드 | 기준 | |
| gcc `-O0` | 같음 | |
| gcc `-O3 -march=native`, gcc `-mfma` | 같음 | `a*b+c`의 FMA 축약을 끄는 pragma + `-ffp-contract=off` |
| clang `-O2`, `-O3 -march=native` | 같음 | 같은 pragma |
| AArch64 (qemu) | 같음 | FMA 축약 금지 (ARM64는 축약이 기본) |
| s390x 빅엔디언 (qemu) | 같음 | 해시·RPC 인자·전송을 리틀엔디언으로 |
| Windows x86-64 (MinGW + wine) | 같음 | Winsock, 바이너리 stdout |
| WebAssembly (`--target wasm32`, clang 18, node 22) | 같음 (arena·boids·village·격자 프로그램) | 자체 C 라이브러리(`sijo_wasm.h`), `fmodf`를 비트 연산으로 정확히, 비트랩 float → int 변환(`-mnontrapping-fptoint`) |
| x87 (`-mfpmath=387`) | 빌드 거부 | 초과 정밀도가 결과를 바꾸므로 `#error` |
| `-ffast-math` | 빌드 거부 | `#error` |
| `Math.Sin`/`Cos` 등 | 같음 | libm 대신 자체 구현 |
| 숫자 → 문자열 | 같음, .NET 8과도 같음 | printf 대신 자체 구현(`123456789f` → `123456792`처럼 C#과 같은 문자열) |

추가로 확인한 것:
- x86-64 Linux 서버에 x86-64 Linux·Windows(wine)·ARM64(qemu)·s390x 빅엔디언(qemu) 클라이언트가 함께 붙어도 모든 클라이언트의 복제 상태 해시가 서버와 같습니다(RPC 포함).
- 수학 함수는 float 입력 2³²개 전부(`Sin`, `Cos`, `Tan`, `Asin`, `Acos`, `Atan`, `Exp`, `Log`, `Log2`, `Log10`)와 무작위 5천만 쌍(`Atan2`, `Pow`)을 검사했습니다. 오차는 최대 1ulp이고, `Asin`·`Acos`·`Exp`·`Log2`는 모든 입력에서 정확히 반올림됩니다.
- 숫자 서식은 float 70만 개 × 서식 10종이 .NET 8 출력과 바이트 단위로 같고, 파서는 32만 개 문자열에서 정확히 반올림하는 파서와 같은 값을 냅니다(glibc `strtof`는 비정규 수 12건에서 틀림).

## 11.3 문서만 아는 에이전트의 교차 언어 검증

에이전트 4개에게 Sijo 문서·예제·컴파일러 바이너리만 주고(컴파일러 소스는 주지 않음), 각자 과제를 Sijo와 다른 언어로 작성해 출력을 비교하게 했습니다. 다른 언어 구현은 문서와 실험으로 파악한 실행 규칙을 따라 작성했습니다. 실행 순서 규칙은 4.9절에 있습니다.

| 에이전트 | 과제 | 언어 | 결과 |
|---|---|---|---|
| sim | 공 1천~5만 개 물리: 충돌·반사·재생성, `Random`, `Sin`/`Cos`, 근접 질의 | Sijo, C++, C#, Rust, Go, Java, JavaScript, Python | 600틱 출력이 모두 같음 |
| algo | A* 경로 찾기, 정렬, FNV 문자열 해시, 단어 빈도, int·float 경계값 | Sijo, C++, C#, Rust, Go, Python | 모두 같음 |
| rules | 시스템 규칙(지연 명령, 스냅샷, 범위 필드, 코루틴, `atomic`)을 쓰는 게임 | Sijo, C++, C#, Rust, Python | 모두 같음. 다른 언어 구현이 따른 규칙(틱 번호, 시스템·아키타입 순서, 파괴 순서, 커서로 만난 자기 자신, 메시지 본문이 읽는 값, 범위 포화 순서, `Until`의 즉시 진행 등)은 4.9절 |
| embed | `--lib` 게임을 여러 언어의 호스트에서 구동, 저장·복원 | C, C++, C#, Python, Rust, Go | 그리기 목록·체크섬이 같고, 언어 간 저장·복원도 같음 |

## 11.4 성능

측정 환경: 4코어 x86-64 가상 머신, gcc 13 `-O2`. 모든 구현은 같은 알고리즘·같은 float 연산 순서로 작성했고 출력이 같은지 확인했습니다.

**엔티티 시뮬레이션** (sim, 틱당 ms, 1스레드, 3회 중앙값; 다른 에이전트의 작업과 CPU를 나눠 쓰는 상태에서 측정해 10~20% 오차가 있을 수 있음):

| 엔티티 수 | Sijo | C++ | C# | Rust | Go | Java | JavaScript |
|---|---|---|---|---|---|---|---|
| 1,000 | **0.33** | 0.38 | 0.43 | 0.38 | 0.44 | 0.78 | 0.83 |
| 10,000 | **4.2** | 4.2 | 5.6 | 4.9 | 5.5 | 6.1 | 10.2 |
| 50,000 | 19.6 | **12.2** | 15.4 | 14.4 | 18.0 | 16.7 | 26.2 |

- 1만 개 이하에서는 C++과 같은 수준이고 C#·Rust·Go·Java·JavaScript보다 빠릅니다. 근접 질의는 컴파일러가 증명하고 넣은 공간 격자 덕분입니다(격자를 끄면 1천 개에서 1.1ms).
- 5만 개에서는 C++보다 1.6배 느립니다. 8192행 이상의 격자는 여러 스레드가 만들고(행 구간별 히스토그램 + 스레드 순서의 오프셋 → 직렬 정렬과 같은 결과), 비슷한 5만 개 근접 질의 워크로드의 4스레드 틱은 약 8.4ms입니다.
- **OpenMP 대기 정책**: 다른 프로세스와 CPU를 나눠 쓰는 환경에서는 OpenMP 기본 정책(작업 스레드가 바쁘게 대기)이 크게 느려졌습니다(1천 개, 4스레드: 4.8ms → `OMP_WAIT_POLICY=passive`로 0.33ms). 서버에서 게임 여러 개를 돌리거나 엔진에 넣을 때는 `OMP_WAIT_POLICY=passive`를 권장합니다.

**일반 알고리즘** (algo, 초, 5회 중앙값, 부하 없는 상태에서 다시 측정):

| 과제 | Sijo | C++ | C# | Rust | Go |
|---|---|---|---|---|---|
| A* (512×512 격자, 경로 40개) | 0.63 | **0.37** | 0.86 | 0.50 | 0.53 |
| 정렬 (100만 개 × 5, 직접 구현) | 0.57 | **0.53** | 0.70 | 0.54 | 0.62 |
| 단어 빈도 (200만 단어, Dictionary) | 0.20 | 0.12 | 0.26 | 0.12 | **0.08** |

- 정렬은 C++과 비슷하고, A*·정렬·단어 빈도는 C#보다 빠릅니다. A*와 단어 빈도는 C++의 1.7배입니다.
- **메모리**: 이 과제들은 모든 계산을 `Game.Start` 한 번(한 틱) 안에서 합니다. 지역 리스트와 문자열은 프레임 아레나에 놓이고 틱이 끝날 때 한꺼번에 해제됩니다. 반복 하나에서 만든 임시 값이 그 반복 밖으로 나가지 않는 루프는 아레나를 반복마다 되감아 메모리를 돌려받습니다(3.3.1절).

## 11.5 생성 코드 검토

- 엔티티 시스템은 컴포넌트 배열을 행 단위로 직접 도는 루프가 되고, 루프 안에서 핸들 조회가 없습니다. 쿼리 커서는 (아키타입, 행)으로 단형화됩니다.
- 정수 wrap 도우미(`sijo_add32` 등)는 인라인되어 덧셈 명령 하나로 컴파일됩니다. `--checked`일 때만 오버플로 검사 분기가 들어갑니다.
- 리스트 경계 검사는 루프 범위로 증명되면 제거되고, 남은 검사는 비교 한 번입니다. 패닉 메시지에 쓰는 `.sijo` 위치는 범위를 벗어났을 때만 기록합니다.
- 생성 C는 gcc·clang의 `-O0`/`-O2`/`-O3`, `-Wall -Wextra -pedantic -Werror`에서 경고가 없습니다(테스트 `generated_c_is_warning_free`).
- 결정론을 위한 비용: FMA를 쓰지 않고, 수학 함수는 double 다항식으로 계산합니다. 시뮬레이션 벤치마크에서 Sijo가 C++과 같은 수준이므로 실제 비용은 작습니다.

## 11.6 남은 한계와 C#과 다른 점

| 항목 | Sijo | C# |
|---|---|---|
| 변경 가능성 | 기본이 불변. 바뀌는 지역 변수·매개변수·엔티티 필드와 `this`를 바꾸는 struct 메서드에 `mut`(1.6.2절). foreach 변수, 그 자리에서 선언한 `out` 변수도 불변 | 기본이 변경 가능, `readonly`로 막음 |
| 상수 | 어떤 타입이든 `const`(컴파일 타임에 계산). `readonly`·`static readonly` 없음 | `const`는 기본 타입·문자열만, 나머지는 `static readonly` |
| 값의 범위 | 범위 타입 `int in 0..100`: 양 끝 포함, 모든 쓰기가 포화, 복제 비트 수를 정함(1.6.1절) | 없음. `0..100`은 끝을 빼는 인덱스 범위 |
| 컬렉션 소유권 | `own` 매개변수는 컬렉션을 넘겨받고 호출한 쪽 변수는 이동, 돌려주는 컬렉션은 `own T`(2.4절) | 참조를 공유하고 GC가 해제 |
| 매개변수 모드 | 기본(읽기 전용 빌림), `mut`, `own`, `ref`, `out`. `in` 없음 | 기본은 값 복사(참조 타입은 참조 복사), `in`, `ref`, `out`, `params` |
| 클라이언트 코드, 호스트 함수 | 수식어 `client`, `extern("c_name")`. 특성은 계획기 힌트·검사 표시만(1.6절) | `[DllImport]` 같은 특성 |
| 본문 | `if`/`else`/`while`/`do`/`for`/`foreach`의 본문은 항상 블록(E0031) | 문장 하나도 됨 |
| 선언 | 선언 하나에 이름 하나(E0030), `for` 헤더도 같음 | `int a, b;` 가능 |
| switch 문 | 모든 값을 다루거나 `default:`(E0237) | 값을 빠뜨려도 됨 |
| 재귀 함수 | `[Recursive]` 표시가 필요(E0312) | 표시 없음 |
| 그 밖의 수식어 | `internal`, `sealed`, `partial`, `unsafe`, 멤버를 가리는 `new`, 확장 메서드(`this` 매개변수) 없음(E0028) | 있음 |
| `char` | 유니코드 코드 포인트(21비트, `'😀'`도 한 글자) | UTF-16 코드 단위 (BMP 밖 문자는 두 개) |
| 람다·델리게이트 | 리스트·배열 메서드의 람다는 호출 지점에 인라인. 델리게이트(`Func`/`Action`/`delegate`)는 null이 없고(기본값은 아무것도 하지 않음), 캡처는 값 복사(`mut` 지역 변수·`ref` 매개변수·컬렉션은 캡처 불가), `this`를 캡처한 람다는 참조를 통해 읽고(시작 시점 값) 지연 쓰기, 캡처한 엔티티가 파괴되면 호출은 아무 일도 하지 않음, `==`·멀티캐스트(`+=`)·`var f = x => ...` 없음 | 변수 캡처(참조), null 델리게이트 호출은 예외, 멀티캐스트, C# 10의 자연 타입 |
