# Sijo 언어 설계 — 0. 개요와 설계 원칙

> **Sijo(시조)** — 세 줄의 정해진 형식을 지키는 한국의 정형시. Epic의 Verse(시)에서 이름을 이었고, 시조가 엄격한 형식 안에서 자유롭게 노래하듯 "단 하나의 규칙"(0.3절) 안에서 게임 세계를 자유롭게 기술하는 언어를 목표로 합니다.
> 파일 확장자 `.sijo`, 컴파일러 `sijoc`.

## 0.1 한 문장 요약

**C#처럼 쓰고, Rust처럼 안전하며, 컴파일러가 코드를 ECS·병렬·네트워크·분산 형태로 자동 변환하는 게임 전용 언어.**

프로그래머는 "싱글 플레이어, 싱글 스레드, 객체지향" 코드처럼 작성합니다.
컴파일러는 게임 전체를 **닫힌 세계(closed world)** 로 보고 전체 프로그램 분석을 해서 다음을 결정합니다.

| 프로그래머가 쓰는 것 | 컴파일러가 만드는 것 |
|---|---|
| `class Ship : Entity { mut Vec2 Pos; ... void Update(float dt) }` | 필드 접근 패턴으로 묶은 **컴포넌트**, SoA **아키타입 테이블**, **시스템** |
| 평범한 메서드 호출, 필드 대입 | 읽기/쓰기 집합, **충돌 없는 병렬 스테이지 스케줄** |
| `client void Render()` | **복제할 필드 자동 추론**, 비트 단위 양자화, 델타 압축 직렬화 코드 |
| `mut var hits = new List<Ship>();` | 탈출 분석 → **프레임 아레나/스택/엔티티 소유 힙** 배치, 해제 코드 자동 삽입 |
| `other.Hp -= 10;` | 결정론적 **지연 명령(커맨드)** — 스레드/서버 샤드 경계를 넘는 메시지와 동일 |
| `mut int in 0..100 Hp` | 7비트 양자화 + 쓰기 지점 포화(clamp) 삽입 |

## 0.2 왜 새 언어인가 — 기존 접근의 한계

조사한 기존 기술과 그 한계(자세한 출처는 `09-references.md`):

- **Verse (Epic)**: 실패 컨텍스트(`<decides>`), 트랜잭션(`<transacts>`) 롤백, 구조적 동시성(`spawn/race/sync`), 서버 권한 복제. UE6(2026-11 발표)은 Actor/Blueprint를 버리고 Verse + Scene Graph(엔티티/컴포넌트)로 이동합니다. 하지만 문법이 기존 게임 개발자에게 낯설고(함수형-논리형), 런타임은 VM 기반이며, ECS 데이터 레이아웃 최적화는 언어가 자동으로 해주지 않습니다.
- **Rust**: 메모리·데이터 레이스 안전성은 최고 수준이지만, 수명 주석·빌림 검사기와의 씨름이 게임플레이 프로그래밍(그래프형 객체 관계가 많음)에서 생산성을 떨어뜨립니다. Bevy는 이를 ECS로 우회합니다.
- **C# / Unity DOTS + Burst**: 문법은 친숙하지만 ECS를 쓰려면 프로그래머가 직접 `IComponentData`, `SystemBase`, `[ReadOnly]` 등을 손으로 분해해야 합니다. Burst는 job 구조체에서 no-alias를 추론해 벡터화하지만, 그건 *프로그래머가 이미 ECS로 분해한 뒤*의 이야기입니다.
- **Unreal Iris / Netcode for Entities**: 양자화·델타 압축·우선순위화를 제공하지만 `[GhostField(Quantization=100)]`처럼 수동 주석이 필수이고, 무엇을 복제할지 사람이 정합니다.
- **SpatialOS**: 공간 분할 + 컴포넌트 단위 권한 이양으로 서버 부하를 분산했지만, 게임 코드가 분산을 의식하고 작성돼야 했고 권한 이동 시점의 디버깅이 어렵다는 문제가 있었습니다.

**Sijo의 가설**: 위 기술들의 *자동화되지 않은 부분*은 대부분 "언어가 프로그램의 데이터 흐름을 모르기 때문"입니다. 게임은 배포 시 닫힌 세계이므로 **컴파일러가 전체 프로그램의 필드 접근, 효과(effect), 값의 범위, 탈출 여부를 정적으로 알 수 있고**, 그 정보로 사람이 하던 분해를 대신할 수 있습니다.

## 0.3 핵심 실행 모델 — "단 하나의 규칙"

Sijo의 모든 자동화(ECS 병렬화, 결정론, 네트워크 분산)는 다음 하나의 의미론 규칙 위에 서 있습니다.

> **시스템 규칙 (System Rule)**
> 한 틱(tick) 안에서 시스템(`Update` 등)은 소스 순서대로 실행되는 것처럼 동작한다.
> 하나의 시스템 안에서 각 엔티티의 코드는
> 1. **자기 자신의 상태는 즉시** 읽고 쓴다.
> 2. **다른 엔티티의 상태는 시스템 시작 시점의 스냅샷**으로 읽는다.
> 3. **다른 엔티티에 대한 쓰기·메서드 호출·생성(Spawn)·파괴(Destroy)는 지연 명령**이 되어, 시스템이 끝날 때 결정론적 순서(엔티티 순서 → 프로그램 순서)로 적용된다.

이 규칙의 결과:

- **모든 시스템은 자동으로 데이터 병렬**입니다. 엔티티 i의 갱신이 엔티티 j의 갱신 결과에 의존할 방법이 없으므로, 컴파일러는 엔티티 순회를 스레드·SIMD·다른 서버로 자유롭게 나눌 수 있습니다.
- **결정론**: 실행 결과가 스레드 수, 샤드 수, 실행 순서와 무관합니다. 리플레이·롤백·록스텝·서버 이전에 필수입니다.
- **분산 투명성**: "다른 엔티티에 대한 지연 명령"은 같은 스레드의 버퍼든, 다른 코어든, 다른 서버 샤드든 **같은 메시지**입니다. 엔티티가 서버를 옮겨 다녀도 게임 코드는 바뀌지 않습니다.
- 이는 Verse의 트랜잭션 의미론을 "시스템 단위 스냅샷 격리 + 교환 가능한 병합"이라는 훨씬 싼 형태로 구현한 것입니다. Rust의 "공유 XOR 변경(aliasing XOR mutation)"을 *시간 축*으로 분리한 것이라고도 볼 수 있습니다 — 공유된 것(다른 엔티티)은 읽기 전용 스냅샷, 변경 가능한 것(자기 자신)은 배타적.

이 규칙이 C#과 다른 유일한 지점은 "다른 엔티티에 쓴 값을 같은 시스템 안에서 다시 읽으면 이전 값이 보인다"는 것입니다. 컴파일러는 이런 코드를 찾아 **경고**합니다(`W0201`).

## 0.4 설계 원칙

1. **친숙함 우선 (C# 문법)**: C# 개발자가 첫날부터 읽고 쓸 수 있어야 합니다. 새 키워드는 최소화하고 C#에 이미 있는 개념(`ref`/`out`, 특성 `[...]`, `is` 패턴, 보간 문자열)을 재활용합니다. C#에 없는 것은 범위 타입(`int in 0..100`)과 수식어 `mut`·`own`·`client` 정도이고, C#에서 한 가지 일을 여러 방법으로 쓰는 것(`readonly`와 `const`, `in` 매개변수 등)은 Sijo에서 한 가지로 씁니다(1.6절).
2. **안전은 기본, 비용은 0에 수렴 (Rust의 안전성)**: null 없음, 데이터 레이스 없음, 해제 후 사용 없음, 정의되지 않은 동작 없음. 단, 수명 주석이나 빌림 검사기와의 씨름 없이 — 안전성 증명의 대부분을 *의미론*(시스템 규칙, 값 의미론, 2급 참조, 세대 핸들)이 대신합니다.
3. **추론이 주석보다 낫다, 주석은 계약이다**: 복제 여부, 양자화 비트, 할당 위치, 컴포넌트 분해, 병렬성은 추론합니다. 사람이 쓰는 표시(범위 타입 `int in 0..100`, `client` 수식어)는 "힌트"가 아니라 컴파일러가 검증·강제하는 **계약**입니다. 특성(`[Precision]`, `[Replicated]` 등)은 계획기에 주는 힌트이고, 지워도 서버의 시뮬레이션 결과는 같습니다(1.6절).
4. **설명 가능한 최적화**: 공격적인 자동 최적화는 블랙박스가 되기 쉽습니다. `sijoc explain`은 모든 결정(왜 이 필드가 복제되는지, 왜 이 시스템이 직렬 실행되는지, 왜 이 리스트가 힙에 있는지)을 근거와 함께 보고합니다.
5. **결정론은 협상 불가**: 같은 입력이면 비트 단위로 같은 결과. 난수조차 (시드, 틱, 엔티티, 호출 지점)의 해시인 카운터 기반 RNG로 결정론적입니다.
6. **점진적 전문가 모드**: 자동 결정이 마음에 들지 않으면 `[Component("Motion")]`, `[Replicated]`, `[Precision(0.1)]` 등으로 덮어쓸 수 있습니다. 기본값은 자동, 탈출구는 명시.
