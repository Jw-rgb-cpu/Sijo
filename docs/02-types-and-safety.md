# 2. 타입 시스템과 안전성 — "Rust 수준의 보장, C# 수준의 마찰"

## 2.1 보장하는 것

| 위험 | Rust의 해법 | Sijo의 해법 |
|---|---|---|
| null 역참조 | `Option<T>` | 엔티티 핸들만 nullable(`T?`), 역참조 전 `is T x` 검사 필수 (흐름 민감) |
| 해제 후 사용 (UAF) | 소유권 + 수명 | 엔티티는 **세대 핸들** + 구조 변경 지연 → 검사한 핸들은 시스템 끝까지 유효 |
| 댕글링 참조 | 수명 주석 | 참조는 **2급** (저장·반환 불가) → 주석 불필요 |
| 데이터 레이스 | `Send/Sync`, `&mut` 배타성 | **시스템 규칙**(자기=배타적 쓰기, 타인=스냅샷 읽기) + 가변 전역 금지 |
| 별칭 변경 (aliasing mutation) | 빌림 검사기 | 호출 지점 **배타성 검사** (`ref` 인자 겹침 금지) |
| 의도하지 않은 변경 | 기본 불변 (`let` / `let mut`) | **기본 불변**: `mut`으로 선언한 변수·매개변수·필드만 바뀜(E0310, 2.3.1절) |
| 이중 해제/누수 | `Drop`, 이동 | 값 의미론 + **마지막 사용 이동 추론** + 시그니처의 `own` + 영역 배치 |
| 정수 오버플로 UB | debug 패닉 / release wrap | 항상 정의됨(2의 보수 wrap), `--checked`로 트랩. 범위 타입(`int in 0..100`)은 모든 쓰기를 포화 |
| 0으로 나누기, 범위 밖 인덱스 | 패닉 | 런타임 검사 (정적으로 증명되면 제거) |
| 비결정론 | (보장 안 함) | 결정론적 RNG, 결정론적 명령 적용 순서, 정렬된 병합 |

## 2.2 값 타입과 엔티티

- `struct`는 순수 값입니다. 대입은 복사이고, 별칭이 없으므로 "공유 가변 상태"가 존재하지 않습니다.
- 엔티티(`class : Entity`)는 값이 아니라 **월드에 있는 행(row)** 입니다. 변수에 담기는 것은 `{index, generation}` 핸들(8바이트)입니다.
  - 파괴되면 generation이 증가하므로 오래된 핸들은 자동으로 무효가 됩니다 (Vale의 generational reference와 같은 원리를 엔티티 단위로 적용, 검사 비용은 시스템당 한 번 수준).
  - 필드에 저장된 엔티티 참조는 반드시 `T?` 타입입니다. 대상이 언제든 파괴될 수 있기 때문입니다.
  - `this`와 `Query<T>()` 루프 변수는 **살아 있음이 보장**됩니다(타입 `T`). 구조 변경(파괴)은 시스템 끝에서만 일어나므로 시스템 실행 중엔 절대 사라지지 않습니다.

```csharp
public Ship? Target;
...
Target.Hp -= 1;                 // 오류 E0301: nullable 핸들 'Target'을 역참조할 수 없습니다. 'is Ship t'로 검사하세요
if (Target is Ship t)           // OK: t는 이 블록 안에서 살아 있음이 보장
{
    t.Hp -= 1;
}
```

## 2.3 2급 참조와 배타성 (Law of Exclusivity)

`ref`/`out` 매개변수와 기본 매개변수(읽기 전용 빌림)는 저장할 수 없는 일시적 참조입니다. 호출 지점에서 컴파일러는 **같은 저장 위치가 `ref`로 두 번, 또는 `ref`와 다른 인자로 동시에 전달되지 않는지** 검사합니다.

```csharp
static void Swap(ref Vec2 a, ref Vec2 b) { var t = a; a = b; b = t; }

Swap(ref Pos, ref Pos);         // 오류 E0402: 'Pos'가 배타적(ref) 인자로 두 번 전달됨
Swap(ref Pos, ref Vel);         // OK: 서로 다른 필드
Swap(ref P.X, ref P.Y);         // OK: 서로 다른 하위 경로 (경로 기반 분리)
```

같은 검사가 컬렉션의 별칭도 막습니다(E0402).

- `own` 매개변수로 옮기는 컬렉션을 같은 호출의 다른 인자로도 넘길 수 없습니다(`H(g[0], g)`): 호출된 함수가 그 컬렉션을 갖고 바꾸거나 해제하는 동안 다른 인자가 그것을 읽게 되기 때문입니다.
- 이 엔티티의 컬렉션 필드(또는 그 원소)를 빌려주는 호출이 그 필드를 바꾸는 메서드이면 오류입니다(`Peek(Keep)` 안에서 `Keep = ...`): 빌린 쪽이 다시 할당되거나 해제된 저장소를 읽게 됩니다. 복사본(`Keep.Clone()`)을 넘기거나, 호출된 메서드가 필드를 직접 읽게 합니다.

이 규칙 덕분에 생성 코드의 모든 `ref` 포인터는 C의 `restrict`로 표시될 수 있습니다(아직 부착하지는 않습니다; 7.3절). Unity Burst가 job 필드에 대해 no-alias를 *추론*하는 것을, Sijo는 언어 수준에서 *보장*합니다.

### 2.3.1 불변이 기본

값은 `mut`으로 선언했을 때만 초기화 뒤에 바뀝니다(1.6.2절). 바뀌는 곳이 선언에 드러나므로 읽는 사람도 컴파일러도 나머지를 고정된 값으로 봅니다.

```csharp
public class Ship : Entity
{
    public ETeam Side;                 // Spawn에서 정하고 바뀌지 않음
    public mut int in 0..100 Hp = 100;

    public void Update(float dt)
    {
        int limit = 10;
        limit += 1;                    // 오류 E0310: 'limit' is immutable: declare it 'mut' to change it
        Side = ETeam.Blue;             // 오류 E0310: field 'Side' is immutable: it is set when the entity is spawned
        Hp -= 1;                       // OK
    }
}
```

- 바뀌지 않는 엔티티 필드는 생성할 때 복제된 뒤로 그 필드의 변경을 보낼 일이 없습니다. 다른 엔티티가 읽어도 해저드(4.6절)가 되지 않아 이중 버퍼가 필요 없습니다.
- 빌린 매개변수는 읽기만 하므로 호출한 쪽 값이 몰래 바뀌지 않습니다. 바꾸려면 `ref`(호출 지점에 `ref`가 보임)나 `mut own`(소유권이 넘어감)을 씁니다.
- 리스트·사전의 변경(`Add`, `Remove`, `xs[i] = v` 등)도 `mut` 바인딩에서만 됩니다. 그래서 `mut`이 없는 컬렉션은 순회하는 동안 바뀔 수 없다는 것이 선언만 봐도 보입니다.

## 2.4 이동 의미론과 `own`

`List<T>`처럼 버퍼를 소유하는 값은 복사가 비쌉니다. Sijo는 Rust처럼 **이동(move)** 을 기본으로 합니다. 이동은 호출 지점에 쓰지 않고, 소유권이 넘어가는 곳은 함수 시그니처의 `own`이 보여 줍니다.

- 대입 시점이 원본의 **마지막 사용**이면 → 자동 이동 (비용 0)
- 이후에도 원본을 사용하면 → 오류 `E0501`과 함께 `.Clone()` 제안
- 함수 인자는 기본이 *빌림*이므로 이동이 일어나지 않음 (가장 흔한 경우)
- `own` 매개변수는 컬렉션을 넘겨받습니다. 호출한 쪽 변수는 호출로 이동하므로 그 뒤에 쓰면 `E0501`입니다. 엔티티 필드는 그 엔티티가 소유하므로 넘길 수 없고(`E0502`), `.Clone()`을 넘깁니다.
- 컬렉션을 돌려주는 메서드는 반환 타입에 `own`을 씁니다(`own List<int> Make()`). 받은 쪽이 소유합니다. 빠뜨리면 `E0505`.
- 이동 검사는 실행 흐름을 따라갑니다. 이동 뒤에 `return`·`break`·`continue`·`fail`로 나가면 그 뒤의 코드에는 영향이 없고(`if (c) { Take(a); return; } Use(a);`는 됨), `?:`와 switch 식의 갈래는 서로 다른 경우이므로 각 갈래에서 같은 변수를 옮겨도 됩니다. 반복문은 다음 반복까지 따라가므로 반복마다 옮기면 `E0501`입니다(옮긴 뒤 바로 나가면 됨). `foreach`가 순회하는 리스트를 본문에서 옮기는 것도 같습니다.
- 람다 본문은 원소마다 실행되므로, 바깥 컬렉션을 람다 안에서 옮기면 `E0501`, 람다가 순회하는 리스트를 옮기면 `E0406`입니다.
- `await`를 넘어 사는 지역 변수도 보통 지역 변수와 똑같이 옮깁니다.

```csharp
public mut List<SVec2> Trail;

public void Update(float dt)
{
    mut var path = new List<SVec2>();
    path.Add(Pos);
    Trail = path;          // path의 마지막 사용 → 이동. path 버퍼 소유권이 엔티티로 넘어감
    path.Add(Pos);         // 오류 E0501: 이동된 값 'path' 사용. 'Trail = path.Clone();'을 고려하세요
}

public static own List<SVec2> MakeRoute(int n) { ... }     // 돌려주는 컬렉션: 호출한 쪽이 소유
public static void Keep(mut own List<SVec2> points) { ... } // 호출이 컬렉션을 가져감

var route = MakeRoute(4);
Keep(route);             // route가 Keep으로 이동 (호출 지점에는 표시가 없음)
Print($"{route.Count}"); // 오류 E0501: 이동된 값 'route' 사용
Keep(Trail);             // 오류 E0502: 엔티티 필드는 이동할 수 없음 → Keep(Trail.Clone())
```

Koka의 Perceus/FBIP가 참조 카운팅 연산을 정적으로 제거하고 Lobster가 RC 연산의 ~95%를 컴파일 타임에 없애는 것과 같은 방향이지만, Sijo는 엔티티 그래프가 핸들로 분리되어 있어 **RC 자체가 필요 없습니다** (공유는 핸들로, 소유는 값으로).

## 2.5 컨텍스트 안전성 (서버/클라이언트)

모든 함수는 실행 컨텍스트를 가집니다: 서버(기본), 클라이언트(`client` 수식어), 공유(순수, 양쪽 가능).

- `client` 코드는 시뮬레이션 상태를 **직접 쓸 수 없습니다** (`E0601`). 서버 권한을 언어 수준에서 강제합니다. 상태를 바꾸는 엔티티 메서드를 호출하면 자동으로 RPC 요청이 됩니다(5.6절).
- 서버 코드는 `Draw.*` 같은 클라이언트 API를 호출할 수 없습니다 (`E0602`).
- 순수 함수(`struct` 연산자 등)는 양쪽에서 쓰입니다 — 이것이 **예측(prediction)** 의 기반입니다 (6장).
