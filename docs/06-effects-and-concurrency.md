# 6. 효과 시스템, 트랜잭션, 동시성

## 6.1 효과 추론

모든 함수의 효과를 호출 그래프 위에서 고정점 반복으로 추론합니다. 사람이 `<transacts>`, `<decides>`처럼 쓰는 Verse와 달리 **기본은 추론**이고, `[Pure]` 특성과 `client` 수식어는 컴파일러가 검증하는 계약입니다.

| 효과 | 의미 | 쓰임 |
|---|---|---|
| `pure` | 읽기만, 출력 없음 | 컴파일 타임 평가(CTFE), 공통식 제거, 클라이언트/서버 공유 |
| `reads(C...)` | 컴포넌트 C 읽기 | 스케줄링, 복제 추론 |
| `writes(C...)` | 자기 컴포넌트 쓰기 | 스케줄링, 해저드 |
| `defers(C...)` | 원격 쓰기/호출 | 명령 버퍼, 샤드 간 메시지 |
| `structural(T...)` | Spawn/Destroy | 스케줄링 |
| `io` | Print | 병렬화 판정 |
| `client` | Draw.* | 컨텍스트 검사 |
| `random` | Random.* | 결정론적 RNG 시드 배정 |

## 6.2 실패와 트랜잭션: `atomic` / `fail`

Verse의 failure context + `<transacts>` 롤백을 C# 문법에 맞게 가져왔습니다.

```csharp
public void TryBuy(int price)
{
    atomic
    {
        Gold -= price;
        Inventory += 1;
        if (Gold < 0)
        {
            fail;                // 블록 안의 모든 효과가 롤백됨
        }
        Spawn(new Receipt { ... });
    }
}
```

**구현 — 정적 실행 취소 로그**: 컴파일러는 `atomic` 블록의 쓰기 집합을 정적으로 알기 때문에, 블록 진입 시 *그 필드들만* 저장하고 명령 버퍼 길이를 기록합니다. `fail`이면 필드를 복원하고 명령 버퍼를 잘라냅니다. 런타임 STM 로그가 필요 없습니다.

- `atomic` 블록 안에서 롤백할 수 없는 효과(`Print`, `Draw.*`·`Net.View`, `extern` 호스트 함수)는 오류 `E0701`. 출력은 블록 뒤로 옮깁니다(블록이 실패하지 않았을 때만 실행됨). 다른 엔티티에 보내는 메시지는 지연 명령이므로 그 본문이 출력해도 됩니다.
- 지연 명령(원격 쓰기·메시지·`Destroy`·RPC)과 `Spawn`은 아직 적용 전이므로 버퍼를 자르는 것만으로 롤백됩니다 — 시스템 규칙이 트랜잭션을 싸게 만듭니다. 블록이 부른 메서드가 생성한 엔티티도(병렬 시스템이면 스레드별 생성 테이블에서) 버려지고, 그 엔티티가 가진 리스트는 해제됩니다.
- 생성 코드: 블록 진입 시 쓰기 집합의 값 필드·바깥 지역 변수만 저장하고, 명령 버퍼 길이와 아키타입별 생성 행 수를 기록합니다. `fail`은 `goto`로 복원 코드로 점프합니다. 런타임 비용은 저장한 필드 수에 비례합니다. 자기 블록의 `fail`이 없는 블록은 되돌릴 일이 없으므로 아무것도 저장하지 않습니다.

**컬렉션**: 리스트·배열·사전의 변경도 롤백됩니다 — 지역 변수, `ref`/`out` 매개변수, 이 엔티티의 컬렉션 필드(코루틴이 await 너머로 들고 있는 지역 변수 포함), 컬렉션의 컬렉션, `Add`·`Insert`·`RemoveAt`·`Remove`·`Clear`·`Sort`·`Reverse`·`RemoveAll`·`Array.Fill`·원소 쓰기(`xs[i] = v`, `xs[i] += 1`, `xs[i].X = 1`, `ps[i].Move()`)·사전의 `d[k] = v`·`Add`·`Remove`·`Clear`, 컬렉션 바꾸기(`xs = new List<int>()`), `ref` 인자로 넘겨 바꾸기, 이 엔티티의 메서드가 필드를 바꾸는 것까지 모두입니다. 컴파일러는 블록마다 바뀌는 컬렉션을 정적으로 알고 둘 중 싼 방법을 고릅니다.

| 블록 안의 변경 | 실행 취소 로그 | 비용 |
|---|---|---|
| 그 컬렉션에 `Add`만 함 (`Log.Add(...)`) | 진입 시 길이 하나 | 진입 시 정수 하나, `fail` 때 늘어난 원소만 버림(안의 리스트는 해제) |
| 그 밖의 변경 | 블록 안에서 **처음 바뀌기 직전에** 깊은 복사(copy-on-write). 복사본은 원본과 같은 메모리 영역(프레임 아레나/힙)에 둠 | 그 컬렉션이 실제로 바뀐 경우에만 크기에 비례. `fail`이면 바뀐 컬렉션을 해제하고 복사본을 제자리에 두고, 끝까지 가면 복사본을 해제 |

```csharp
public bool Buy(int item)
{
    atomic
    {
        if (!Stock.Remove(item))   // 처음 바뀌기 직전에 Stock 복사
        {
            fail;                  // Stock·Gold·Prices·Log·Spawn·메시지 모두 원래대로
        }
        Gold -= Prices[item];
        Prices[item] += 1;         // Prices도 처음 바뀔 때 복사
        Log.Add($"buy {item}");    // Add만: 진입 시 길이만 기록
        Spawn(new Receipt { Items = new List<int> { item } });
        if (Gold < 0)
        {
            fail;
        }
        return true;               // return은 블록을 커밋(복사본 해제)하고 나감
    }
    return false;
}
```

**중첩과 블록 나가기**

- `atomic`은 중첩됩니다. 안쪽 블록의 `fail`은 안쪽 블록만, 바깥 블록의 `fail`은 안쪽에서 커밋한 것까지 모두 되돌립니다. 바깥 블록이 아직 복사하지 않은 컬렉션을 안쪽 블록이 복사했다면, 안쪽 블록이 커밋할 때 그 복사본이 그대로 바깥 블록의 복사본이 됩니다(그때까지 바깥 블록에서는 바뀌지 않았으므로 같은 상태) — 다시 복사하지 않습니다. 안쪽 블록에서 `Add`만 하는 컬렉션은 안쪽 블록에는 길이만 기록하고, 복사가 필요한 바깥 블록이 그 자리에서 복사합니다.
- `return`(값이 있어도), `break`, `continue`는 블록을 정상적으로 떠나는 것이므로 C#의 자연스러운 읽기대로 **커밋**합니다: 쓴 것은 남고, 지나는 모든 블록의 복사본이 해제됩니다. 값을 돌려주는 식은 커밋 전에 계산됩니다. 블록이 `return`/`break`로 끝나고 자기 `fail`이 없으면 블록 뒤는 도달할 수 없는 것으로 봅니다(메서드 끝의 `return`, switch 구간 끝의 `break`가 필요 없음). `fail`이 있으면 블록 뒤로 이어지므로 C#처럼 그 뒤에 `break`/`return`이 있어야 합니다.
- `await`는 블록 안에서 오류 `E0803`입니다: 트랜잭션은 한 틱 안에서 끝나야 합니다(다른 시스템이 그 사이의 상태를 보게 되므로). 블록을 await 앞에서 끝내고 뒤에서 새로 시작합니다. await와 await 사이의 `atomic`은 됩니다.
- `fail`은 블록 밖에서 오류 `E0703`, `break`/`continue`는 블록 밖으로 나가더라도 그 블록을 감싼 반복문이 있어야 합니다(`E0233`). struct 메서드 안의 `atomic`은 `E0705`: 그 메서드를 부르는 쪽에서 감싸면 struct의 변경은 그 struct를 담은 변수·필드와 함께 되돌려집니다.
- 반복마다 프레임 메모리를 되돌려 주는 반복문(3.3.1절)은, 실행 취소 로그가 반복문 밖에서 선언된 컬렉션을 그 반복 안에서 복사할 수 있으면 되돌려 주지 않습니다(복사본이 `fail` 때 제자리로 돌아가므로).

## 6.3 코루틴과 구조적 동시성

Verse의 `sync / race / rush`를 C#의 `async/await` 문법으로 씁니다(문법은 1.10절).

```csharp
public async void Patrol()
{
    while (true)
    {
        await MoveTo(A);
        await Wait(2.0);
        int winner = await Race(MoveTo(B), Until(bEnemySeen));   // 먼저 끝난 갈래의 번호, 나머지는 취소
    }
}
```

- `await NextTick() / Wait(t) / Until(c)`와 다른 async 메서드를 기다리는 `await M(args)`: 기다리는 쪽이 매 틱 그 메서드의 상태 기계를 한 단계 이어서 실행하고, 끝나면 다음 줄로 넘어갑니다. 프레임이 같은 엔티티의 숨은 필드에 있으므로 할당이 없습니다.
- `await Race(...)`는 먼저 끝난 갈래가 이기고 나머지는 취소하며 이긴 갈래의 번호가 값입니다. `await Sync(...)`는 모든 갈래가 끝날 때까지 기다립니다. 갈래마다 상태 필드가 있으므로 취소는 그 상태를 "끝남"으로 바꾸는 것뿐입니다.
- `await Rush(...)`는 먼저 끝난 갈래에서 이어 가고, 끝나지 않은 메서드 갈래는 배경에서 끝까지 실행합니다. 배경 갈래는 숨은 비트 집합에 표시되고, 코루틴 함수가 매 틱 재개 지점으로 가기 전에 한 단계씩 실행합니다.
- 엔티티와 무관하게 떼어 내는 Verse의 `spawn`은 없습니다(로드맵 8.3).

**코루틴 상태 = 엔티티의 숨은 필드**: 각 `async` 메서드는 상태 기계로 바뀌고, 그 상태(재개 지점, 타이머, await를 넘어 살아 있는 지역 변수)는 엔티티의 숨은 필드가 되어 일반 필드처럼 컴포넌트로 묶입니다(4.11절). 대기 중인 코루틴은 그 필드를 가진 엔티티일 뿐이라 힙 할당이 없고, 수천 개의 코루틴도 SoA로 순회되며, 코루틴은 엔티티 시스템으로 스케줄됩니다.

## 6.4 결정론적 난수

`Random.Float(a, b)`는 전역 상태가 아니라 `hash(월드 시드, 틱, 엔티티 ID, 호출 지점 ID, 호출 내 카운터)`로 계산되는 카운터 기반 RNG입니다(SplitMix64 계열).

- 병렬 실행 순서와 무관 → 결정론
- 서버/클라이언트가 같은 값을 계산 가능 → 예측
- 리플레이 시 같은 결과
